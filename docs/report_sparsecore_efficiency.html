Full Occupancy, Empty Decode

Three ways to check whether SparseCore is actually being used well — occupancy across its 32 subcores, achieved throughput per call, and a cross-check against an independent empirical sweep — run against the same encode-heavy and decode-heavy steps as the profiling capture.

32/32 SparseCore subcores active during the encode-heavy step, balanced within ~7%
0/32 SparseCore subcores active during decode — the dense fallback fires instead, by design
9 distinct sc_ragged_gather_v2 calls captured, each moving an identical bf16[262144,2048] shape
64× SparseCore's independently-measured margin over dense at this exact shape, from an earlier sweep

Why occupancy is the first question

ragged_gather_v2.py and ragged_gather_reduce_v2.py make different partitioning decisions for the same 32 SparseCore core-slots (2 cores × 16 subcores), and the difference isn't a style choice.

ragged_gather_v2 splits only the token dimension — every one of the 32 slots gets a contiguous row range and processes the full hidden dimension for those rows, indexed directly by core_index = lax.axis_index(...). It carries no per-partition state, so it's free to use all 32 slots on rows alone.

ragged_gather_reduce_v2 searches for a 2D split in _calculate_num_column_partitions, lines 124-161, subject to a hard assert at lines 631-632: num_row_partitions ≤ num_simd_lanes (8 on this hardware). It packs per-row-partition state — valid-row counts, sort permutations for the segmented reduction — into a vector sized exactly num_simd_lanes, capping distinct row-partitions at 8. With 32 total slots and only 8 usable for rows, the remaining 4× of parallelism is only reachable by also splitting columns.

One kernel hits a hardware/algorithm constraint the other doesn't have, and compensates by borrowing the column dimension. That's the setup for the question this page actually answers: given whichever partition shape a kernel picks, is it actually keeping the hardware busy?

These numbers can't responsibly be turned into a "% of peak" figure. No verified peak-bandwidth spec for this v6e's SparseCore was in hand to compare against, and the achieved figures — several TB/s, all exceeding typical single-chip HBM bandwidth — suggest this is measuring VMEM-tile throughput inside SparseCore's own pipeline rather than raw HBM traffic. Read this as "very high and consistent across all 9 calls," not a calibrated efficiency score. A real spec sheet would turn this into an actual percentage.

Bottom line

All three tests agree, for both steps. Prefill uses SparseCore fully and effectively — full occupancy, high and consistent throughput, backed by an independent sweep that already showed this shape favors SparseCore by a wide margin. Decode correctly avoids it — zero occupancy is the fix working as intended, not an inefficiency to chase. For this capture, at these two steps, SparseCore isn't leaving anything obvious on the table.
