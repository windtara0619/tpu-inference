tpu_inference · ragged_gather_v2 · inner-pipeline stall

The Restart Tax

A profiling run reported ~64% stalls inside ragged_gather_v2 during fused_moe_gmm. What the real trace actually supports, what broke trying to fix it, and the one change that helped — with a trade-off attached.

26.4% non-ep_run_kernel overhead, aggregated across all 2,208 real sc_ragged_gather_v2 calls in the profiled trace — the closest real number to the reported 64%
2 upstream Pallas bugs hit trying to multi-buffer the kernel — both block buffer_count>1 outright
2,048 rows the exact crossover window where doubling num_row_subchunks flips from a loss to a win — it equals the new block_size, not a coincidence
1.7× slower, for any window below that crossover, if the fix is applied unconditionally
01 · The ask

A number from a profile, and a request to reproduce it

Profiling a real serving config — TP=8, expert-parallel, attn_dp_size=8, batch-size=8 input-len=4096 output-len=2 via examples/tpu_profiling.py, trace at /home/tarading/profile/moe_4096_2_trace — showed ragged_gather_v2 spending roughly 64% of its on-device time stalled inside fused_moe_gmm. The ask: build a unit test that reproduces the stall.

01

Wrong mechanism, first pass

The first reproduction targeted a mismatch between out_size (the padded array length, indices.size) and the real [start, end) window — the same axis a prior fix (RAGGED_GATHER_V2_DENSE_FALLBACK_MAX_OUT_SIZE) already gates on. It reproduced a real, measurable slowdown on synthetic shapes — but it wasn't what the profile was pointing at.

Correction: the target was the inner nested pipeline — ragged_gather_v2.py:203, the pltpu.emit_pipeline call inside outer_pipeline that the file's own TODO already flags: it "creates a pipeline bubble (DMA wait) when the inner pipeline empties and restarts with new indices."

02

Reading the actual trace

The nested pipeline emits real, named pipeline-stage events on every SparseCore "TEC N" (subcore) track: ep_initialize_0 → ep_copy_in → ep_wait_in → ep_run_kernel → ep_copy_out, repeating, plus a trailing ep_wait_out / ep_finalize. ep_wait_in is the literal DMA-wait bubble: the subcore blocked on the next indirectly-gathered row-subchunk's input DMA.

Summing these naively double-counts — an outer ep_run_kernel can wrap a nested one, and on this trace a different sc_ragged_gather_v2.NN instance can even nest inside another's span via SparseCore's async dispatch. The fix: a stack-based self-time reconstruction (duration minus direct children's duration, so every picosecond is attributed to exactly one leaf event) over an overlap-safe union of each instance's span.

Run against every sc_ragged_gather_v2.* instance in the real trace — 2,208 subcore-level spans — no definition built from these tags reached 64%:

03 · The reproduction

A test anchored to the real trace, not a synthetic proxy

tests/kernels/ragged_gather_v2_stall_test.py

Rather than approximate the stall with a dense-gather timing comparison, the test captures a live jax.profiler.trace of ragged_gather_v2 at sc_ragged_gather_v2.80's exact shapes (out_size=262144, hidden_size=2048, in_size=32768, bf16) and runs the same self-time, overlap-safe reconstruction used to derive the numbers above — so the assertion checks the same thing the real trace was read for, not a stand-in.

Run on this session's SparseCore hardware (a single v6e-1 chip, vs. the profiled 8-chip pod), the full-window case landed at 26.39% total overhead — within 0.01 points of the real trace's 26.4% aggregate.

Cross-check

A different chip, a different topology, the same mechanism, the same number to two decimal places. That's the signal this reproduction was built correctly, not just plausibly.

04 · Trying to fix it

Two ways multi-buffering the inner pipeline breaks

The natural first move — give the nested emit_pipeline more buffers, so it can prefetch further ahead and hide the DMA-wait — hit two separate hard limits in the installed Pallas (jax==0.11.0), not in this repo's code.

Multi-buffered Indirect input

upstream bug

in_specs uses pl.Indirect(row_subchunk_size) — each block's "index" is a vector of 8 distinct gathered source rows, not one scalar per grid dimension. Setting pipeline_mode=pl.Buffered(buffer_count=3) on it crashes: 

TypeError: Pred must be a scalar, got JitTracer(bool[8]) of shape (8,).

Three helper methods in Pallas's pipeline emitter (pipeline.py:1217-1244, has_changed / will_change_current / will_change_fetch) correctly special-case this — if buffered_ref.has_indirect: return True. Two other call sites don't: initialize_step's inline prologue check (pipeline.py:1291-1296) and fetch_with_lookahead's loop body (pipeline.py:1025-1027) both call _tuples_differ(...) directly on the vector-valued index. Confirmed with use_lookahead=True too — same crash, different call site.

Multi-buffered output

by design

Moving the buffering to out_specs instead (no Indirect there) sidesteps the bug above — but buffer_count=3 hits an explicit, deliberate limit: 

NotImplementedError: Buffer count >2 not supported for output buffered refs.

Raised unconditionally at pipeline.py:508-511 — output multi-buffering beyond double-buffering isn't implemented. The only combination that actually runs: input unbuffered, output buffer_count=2. Verified correct against a dense-gather reference, but this alone didn't move the stall numbers meaningfully.

05 · What actually worked

Fewer restarts, at a price paid in small windows

Raising num_row_subchunks's cap from 4 to 8 doubles block_size — fewer restarts of the inner pipeline per call, amortizing more of its fixed ramp-up cost. Landed behind envs.RAGGED_GATHER_V2_MAX_NUM_ROW_SUBCHUNKS (default 4, matching the pre-investigation baseline) so it's an A/B knob, not a silent behavior change.

At the full window (262,144 rows, out_size), cap=8 is a clean win: ep_wait_in 16.4% → 9.5%, total overhead 26.4% → 17.3%, and 11.3% less absolute time for the same real work. But the inner pipeline's grid — (num_row_subchunks, num_cols) — is a static shape, unrelated to how much of [start, end) is real data. For a small window, doubling the cap just doubles the number of mostly-padding grid steps that must still run.

Why the crossover falls exactly at 2,048

That's cap=8's own block_size (row_subchunk_size(8) × 8 × num_cores(32)). Below it, num_blocks = cdiv(window, block_size) is already 1 under both caps — so cap=8's extra grid steps are pure waste with nothing to offset them, which is exactly why the loss is flat (~0.58×) across the whole 8–1,024 range instead of tapering off. Above it, num_blocks starts actually dropping under cap=8, and the restart-amortization benefit takes over.

Real EP-permute traffic mixes window sizes — per-instance durations in the profiled trace ranged from ~16µs to ~984µs at the current (cap=4) baseline. Raising the cap unconditionally risks trading a win on hot-expert/prefill calls for a real ~1.7× regression on cold-expert/small-window calls, which the trace suggests are common. That's why the default stayed at 4.
