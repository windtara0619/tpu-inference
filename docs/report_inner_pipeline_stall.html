tpu_inference · ragged_gather_v2 · inner-pipeline stall

The Restart Tax

A profiling run reported ~64% stalls inside ragged_gather_v2 during fused_moe_gmm. What the real trace actually supports, what broke trying to fix it, and the one change that helped — with a trade-off attached.

26.4% non-ep_run_kernel overhead, aggregated across all 2,208 real sc_ragged_gather_v2 calls in the profiled trace — the closest real number to the reported 64%
2 upstream Pallas bugs hit trying to multi-buffer the kernel — both block buffer_count>1 outright
2,048 rows the exact crossover window where doubling num_row_subchunks flips from a loss to a win — it equals the new block_size, not a coincidence
1.7× slower, for any window below that crossover, if the fix is applied unconditionally
01 · The ask

A number from a profile, and a request to reproduce it

Profiling a real serving config — TP=8, expert-parallel, attn_dp_size=8, batch-size=8 input-len=4096 output-len=2 via examples/tpu_profiling.py, trace at /home/tarading/profile/moe_4096_2_trace — showed ragged_gather_v2 spending roughly 64% of its on-device time stalled inside fused_moe_gmm. The ask: build a unit test that reproduces the stall.

01

Wrong mechanism, first pass

The first reproduction targeted a mismatch between out_size (the padded array length, indices.size) and the real [start, end) window — the same axis a prior fix (RAGGED_GATHER_V2_DENSE_FALLBACK_MAX_OUT_SIZE) already gates on. It reproduced a real, measurable slowdown on synthetic shapes — but it wasn't what the profile was pointing at.

Correction: the target was the inner nested pipeline — ragged_gather_v2.py:203, the pltpu.emit_pipeline call inside outer_pipeline that the file's own TODO already flags: it "creates a pipeline bubble (DMA wait) when the inner pipeline empties and restarts with new indices."

02

Reading the actual trace

The nested pipeline emits real, named pipeline-stage events on every SparseCore "TEC N" (subcore) track: ep_initialize_0 → ep_copy_in → ep_wait_in → ep_run_kernel → ep_copy_out, repeating, plus a trailing ep_wait_out / ep_finalize. ep_wait_in is the literal DMA-wait bubble: the subcore blocked on the next indirectly-gathered row-subchunk's input DMA.

Summing these naively double-counts — an outer ep_run_kernel can wrap a nested one, and on this trace a different sc_ragged_gather_v2.NN instance can even nest inside another's span via SparseCore's async dispatch. The fix: a stack-based self-time reconstruction (duration minus direct children's duration, so every picosecond is attributed to exactly one leaf event) over an overlap-safe union of each instance's span.

Run against every sc_ragged_gather_v2.* instance in the real trace — 2,208 subcore-level spans — no definition built from these tags reached 64%:

03 · The reproduction

A test anchored to the real trace, not a synthetic proxy

tests/kernels/ragged_gather_v2_stall_test.py

Rather than approximate the stall with a dense-gather timing comparison, the test captures a live jax.profiler.trace of ragged_gather_v2 at sc_ragged_gather_v2.80's exact shapes (out_size=262144, hidden_size=2048, in_size=32768, bf16) and runs the same self-time, overlap-safe reconstruction used to derive the numbers above — so the assertion checks the same thing the real trace was read for, not a stand-in.

Run on this session's SparseCore hardware (a single v6e-1 chip, vs. the profiled 8-chip pod), the full-window case landed at 26.39% total overhead — within 0.01 points of the real trace's 26.4% aggregate.

A different chip, a different topology, the same mechanism, the same number to two decimal places. That's the signal this reproduction was built correctly, not just plausibly.

04 · Trying to fix it

Two ways multi-buffering the inner pipeline breaks

The natural first move — give the nested emit_pipeline more buffers, so it can prefetch further ahead and hide the DMA-wait — hit two separate hard limits in the installed Pallas (jax==0.11.0), not in this repo's code.

Multi-buffered Indirect input

upstream bug

in_specs uses pl.Indirect(row_subchunk_size) — each block's "index" is a vector of 8 distinct gathered source rows, not one scalar per grid dimension. Setting pipeline_mode=pl.Buffered(buffer_count=3) on it crashes: 

TypeError: Pred must be a scalar, got JitTracer(bool[8]) of shape (8,).

Three helper methods in Pallas's pipeline emitter (pipeline.py:1217-1244, has_changed / will_change_current / will_change_fetch) correctly special-case this — if buffered_ref.has_indirect: return True. Two other call sites don't: initialize_step's inline prologue check (pipeline.py:1291-1296) and fetch_with_lookahead's loop body (pipeline.py:1025-1027) both call _tuples_differ(...) directly on the vector-valued index. Confirmed with use_lookahead=True too — same crash, different call site.

Multi-buffered output

by design

Moving the buffering to out_specs instead (no Indirect there) sidesteps the bug above — but buffer_count=3 hits an explicit, deliberate limit: 

NotImplementedError: Buffer count >2 not supported for output buffered refs.

Raised unconditionally at pipeline.py:508-511 — output multi-buffering beyond double-buffering isn't implemented. The only combination that actually runs: input unbuffered, output buffer_count=2. Verified correct against a dense-gather reference, but this alone didn't move the stall numbers meaningfully.

05 · What actually worked

Fewer restarts, at a price paid in small windows

Raising num_row_subchunks's cap from 4 to 8 doubles block_size — fewer restarts of the inner pipeline per call, amortizing more of its fixed ramp-up cost. Landed behind envs.RAGGED_GATHER_V2_MAX_NUM_ROW_SUBCHUNKS (default 4, matching the pre-investigation baseline) so it's an A/B knob, not a silent behavior change.

At the full window (262,144 rows, out_size), cap=8 is a clean win: ep_wait_in 16.4% → 9.5%, total overhead 26.4% → 17.3%, and 11.3% less absolute time for the same real work. But the inner pipeline's grid — (num_row_subchunks, num_cols) — is a static shape, unrelated to how much of [start, end) is real data. For a small window, doubling the cap just doubles the number of mostly-padding grid steps that must still run.

A log-spaced sweep across window sizes, both caps, at the same real shapes, makes the trade-off explicit:

Why the crossover falls exactly at 2,048

That's cap=8's own block_size (row_subchunk_size(8) × 8 × num_cores(32)). Below it, num_blocks = cdiv(window, block_size) is already 1 under both caps — so cap=8's extra grid steps are pure waste with nothing to offset them, which is exactly why the loss is flat (~0.58×) across the whole 8–1,024 range instead of tapering off. Above it, num_blocks starts actually dropping under cap=8, and the restart-amortization benefit takes over.

Real EP-permute traffic mixes window sizes — per-instance durations in the profiled trace ranged from ~16µs to ~984µs at the current (cap=4) baseline. Raising the cap unconditionally risks trading a win on hot-expert/prefill calls for a real ~1.7× regression on cold-expert/small-window calls, which the trace suggests are common. That's why the default stayed at 4.

A stricter definition of "stall": outliers inside ep_run_kernel itself

ep_wait_in is only whatever Pallas's profiler chose to tag as a separate wait state — with multi-buffering blocked (section 04), some of that same DMA-wait can get absorbed inside an ep_run_kernel span instead of being broken out, showing up as an outlier-long call rather than a separate tag. Taking each ep_run_kernel occurrence's own self-time (correcting for the ~80% of calls that nest inside another ep_run_kernel via async dispatch) gives a distribution, not just an aggregate:

What this doesn't show: an end-to-end win

The whole-model device-timeline span (TensorCore + SparseCore combined busy window for the full profiled step) is 1.637s (cap=4) vs 1.651s (cap=8) — flat, within single-iteration (--num-iters 1) noise. A naïve first pass at this — min/max timestamp across the entire trace file — gave a false −32.7% (2.481s→1.670s); that was an artifact of /host:CPU background threads parked in queue.get()/threading.wait() for unrelated reasons, not device work, and had to be excluded. At this workload (a single large prefill + 1 decode step), ragged_gather_v2 isn't on the step's critical path, so a real, independently-confirmed ~10% reduction in its own on-device time doesn't move overall latency here. It may matter more at configs where MoE-permute is a bigger share of the critical path (larger batch/expert counts, decode-heavy workloads).

08 · A different kernel, same question

Does ragged_gather_reduce_v2 have the same row/col lever?

ragged_gather_reduce_v2 is the MoE combine step — gather by topk_argsort_revert_indices, weight, and segmented-reduce topk rows per output token. Unlike ragged_gather_v2 it already splits both row and column axes across cores. The question: is that split tunable, the way ragged_gather_v2's num_row_subchunks turned out to be?

A direct, profiler-grounded bandwidth fit (single SparseCore lane vs. the full 32-lane chip, live-traced elapsed device span, not wall clock) reproduces the same hardware picture found for ragged_gather_v2: 19.160 GB/s per lane, R²=1.000000, scaling to 593.9 GB/s at full 32-lane occupancy — 96.9% of the naive 32× prediction (613.1 GB/s), the same ~3% sub-linear falloff measured for the other kernel. No lane contention, no headroom to reclaim by concentrating work on fewer cores.

At the real production shape (hidden=2048, input_size=262144), num_column_partitions=4 isn't tuned — it's the only value that compiles at all. Two hard constraints converge on it from opposite directions: num_row_partitions ≤ num_simd_lanes(8) forces ncp≥4, while sorted_by_validity_vmem's per-partition buffer blowing the 256KB VMEM budget once num_row_partitions<8 forces ncp≤4. No slack to search over — unlike ragged_gather_v2's row split, this axis has nothing to tune.

The row-subchunk cap: a dead end here

Mirroring RAGGED_GATHER_V2_MAX_NUM_ROW_SUBCHUNKS, a RAGGED_GATHER_REDUCE_V2_MAX_NUM_ROW_SUBCHUNKS knob was added (_calculate_row_tiling had the cap hardcoded to 4, derived from the static padded input_size rather than any real per-partition valid count — so it was always saturated regardless of real work). Raising it to 8 doesn't trade off against small windows the way it did for ragged_gather_v2 — it doesn't compile at all: 

error: 'memref.alloca' op E3000: CompileTimeSparseCoreAllocationFailure:
current allocation offset upper bound (28 words) exceeds the legitimate
user allocatable offset upper bound (27 words) in memory space sflag_tile
when allocating 2 words

Off by a single word. This kernel's nested row/col pipeline carries more per-row-subchunk state (segmented-reduction bookkeeping: sort permutation, destination indices, weights, carry values) than ragged_gather_v2's plain gather, so it hits a hard SparseCore scalar-flag allocator ceiling that the simpler kernel never approached. cap=4 is the ceiling, not a choice.

09 · The real problem

Static partitioning collides with routing skew

With both split axes closed off, a debug hook (MOE_LOG_COMBINE_VALID_ROWS_STATS, gated in fused_moe_gmm.py) was added to read the real, ground-truth valid-row count directly from jnp.sum(mask) on every real production call, rather than estimating it from trace timing.

_preprocess splits each shard's local-expert token range into num_row_partitions=8 equal-sized contiguous index-range slices. valid_rows_mask is indexed in token-major order (it has to be — the segmented reduce sums consecutive topk entries per output token), so a contiguous partition slice is a contiguous batch-position range, not an expert-sorted one. Real MoE routing correlates with token/batch position — content is correlated within a request, and in this benchmark num_tokens/num_row_partitions = 32768/8 = 4096 = input_len exactly, so each partition's slice lines up with one whole request. One request routing heavily toward this shard's local experts, another barely touching them, lands as one overloaded partition and one idle one.

Ruled out: a statistical sizing formula

A num_tokens×topk/devices ± σ formula was considered and directly tested against this ground truth. It fails on two independent counts: the naive uniform-random model (even correcting for the known expert-parallel fraction) overshoots the real mean by 2–35× depending on the call, and its predicted spread (std≈60, tiny relative to the mean) is the opposite shape of what's real (std > mean). No closed-form margin describes a distribution that swings from 0 to 5× on the same call, same layer family, same config.

A narrower, lower-risk idea — skip the inner pipeline's trailing, padding-only row-subchunks in a partition's last (partial) block — was also modeled directly against the real trace. Since only the last block per partition can ever be partial, the waste is bounded per occurrence regardless of how large that occurrence is; total device time is dominated by a handful of large occurrences where the bounded waste is a rounding error. Estimated aggregate saving: 1.80% (1.018×) — real, but small enough to deprioritize against fixing the partitioning itself.

10 · The fix

Interleave row-partitions by token-group rank

RAGGED_GATHER_REDUCE_V2_INTERLEAVE_ROW_PARTITIONS, default false

_preprocess now has an alternate path: instead of valid_rows_mask.reshape(num_row_partitions, -1) (contiguous blocks), it reshapes to (token_groups_per_partition, num_row_partitions, reduce_group_size), transposes, and flattens — assigning token-group t (one output token's topk choices, kept together) to partition t % num_row_partitions by round-robin rank instead of index range. A contiguous run of L valid rows, wherever it falls, now lands ~L/8 in every partition instead of concentrating in one or two. The stable sort-by-validity and the rest of the kernel are untouched — only which original row a given partition slot maps back to changes (local_group*(num_row_partitions*reduce_group_size) + p*reduce_group_size + local_k instead of local + p*row_partition_size).

Correctness

The full ragged_gather_reduce_v2_test.py suite (54 cases, exact numerical comparison against a reference implementation) passes with the flag both off and on. A direct output comparison between the old and new preprocessing on the same kernel, same inputs, is bit-identical.

No shape reproduces the original claim

In every shape tested, P99 TTFT moves by roughly the same magnitude as mean/median TTFT — never dramatically more. There is no evidence anywhere here for an isolated-tail-fix mechanism, and nothing close to a 73% P99 TTFT improvement. What's real and consistent instead: TTFT improves in every shape, by an amount that scales with how prefill-dominated the workload is — roughly 1–4% when a long decode phase dominates E2E time (1,024/1,024), 5–8% when prefill dominates (4,096/2 and 8,192/1).

Decode is neutral, not regressed — and the earlier "broad win" read was an artifact

With a genuine, long decode phase (1,024/1,024), TPOT is flat within noise (+0.1% mean, +0.02% P99) — not the report's claimed ~0.5–3.3% regression, but also not the large win seen in the 4,096/2 shape. That earlier result (TPOT down 6.8–11.3%) came from a shape with only one decode step per request, where TPOT wasn't really isolating steady-state decode behavior — it was picking up the same prefill-driven, system-level effect as every other metric in that run. The 1,024/1,024 shape is the trustworthy read on decode: this flag doesn't meaningfully touch it either way. This is still consistent with the corrected section 10 kernel numbers (interleaved path never slower than contiguous, at every span tested) — there's no kernel-level mechanism for a decode regression, and now no serving-level evidence for one either.

Caveats

Each shape is one run per configuration, both firing all 512 requests at once (--request-rate inf) on a shared TPU pod, so individual percentages carry a few points of run-to-run noise. The consistent direction and rough magnitude across three independently-run, structurally different shapes is a stronger signal than any single run would be, but repeated trials per shape would still sharpen the exact numbers above.

Net, across all three shapes: a real, consistent prefill/TTFT improvement (roughly 1–8%, larger when prefill dominates the workload) with a genuinely neutral effect on decode — not the report's narrow "tail-latency win, decode pays for it" story, and not an unconditional "everything improves" story either.
