01 — The Ask

One Kernel, One Unconditional Choice

ragged_gather_v2 is the SparseCore kernel that permutes hidden_states into expert-sorted order before the MoE expert matmul — once per layer, under expert parallelism, on every forward pass. Its dispatch logic is one branch: 

sc_info = pltpu.get_tpu_info().sparse_core
if sc_info is None:
    return x[indices]   # only for missing hardware, never for speed

# otherwise: always SparseCore, no matter how small the call

Whenever SparseCore hardware is present, the kernel uses it — regardless of how small or narrow the individual call is. That's worth questioning on its own terms: a SparseCore kernel invocation carries real fixed cost before it moves a single byte — DMA descriptor construction, semaphore handshakes, pipeline warm-up. That cost doesn't shrink with the size of the call. If a gather is small enough, the fixed cost can outweigh anything SparseCore's throughput advantage buys back on the actual data movement. The only way to know where that line sits is to benchmark the kernel directly against the dense TensorCore gather already sitting one branch away in its own source file — on identical inputs, across whatever shapes real traffic actually produces.

02 — Capturing What Real Traffic Looks Like

429,312 Calls, Logged Off a Live Server

Rather than guess a synthetic sweep's range, the engine instrumented the kernel first. A diagnostic hook — MOE_LOG_RAGGED_GATHER_V2_STATS, off by default — fires a host-side callback on every real call and logs out_size, hidden_size, dtype, and the [start, end) window, wired directly into ragged_gather_v2 itself and gated by the env flag so it costs nothing when it's off. With the flag on, the engine stood up a real serving stack — the config that actually ships — and drove it with a real load test: vllm serve for Qwen3-30B-A3B at tensor-parallel 8, expert-parallel 8, bfloat16, dp_attention also sharded 8-way over the same eight chips, chunked prefill on, async scheduling on; driven by vllm bench serve at 512 concurrent requests, 1,024-token prompts and generations, request rate uncapped.

One run, 512 concurrent requests, 1,024-token prompts and generations: 429,312 real ragged_gather_v2 calls logged before a single synthetic benchmark ran. Every one of them carried hidden_size=2,048, dtype=bfloat16 — real, fixed values the sweep would anchor to rather than guess at — and out_size landed on one of exactly 12 XLA-compiled bucket sizes:

04 — What the Sweep Shows

What the Sweep Shows

01

Below out_size=2,048, dense wins every single cell — window_fraction never matters

For out_size ∈ {128, 256, 512, 1,024, 2,048}, the SparseCore pipeline's block size (row_chunk_size × num_cores, driven by num_row_subchunks) works out to ≥ out_size itself on this hardware — the kernel can never use more than one pipeline block no matter where end lands, so window_fraction has zero effect on SparseCore's cost at these sizes. It still loses to dense every time, by 1.7×–2.4×, purely on fixed per-call SparseCore overhead that a single block can't amortize.

02

At the dominant real bucket, out_size=4,096, the crossover isn't smooth — it's a hard step at window=1,024

On this v6e-8 (SparseCore: 8 lanes × 2 cores × 16 subcores), the base block is 256 rows and num_row_subchunks caps at 4, so out_size=4,096 compiles to a fixed 1,024-row block size. Timing confirms it precisely: the dense÷SC ratio sits flat at ≈1.00× for every window ≤ 1,024 (1 block, true parity, not a near-miss), then drops to a flat 0.72× the instant window crosses 1,024 into a second block, 0.56× at a third, and 0.46× at a fourth (the full 4,096-row window). There is no gradual crossing here, only edges.

03

Because block size stops scaling past the cap, the largest sizes are where SparseCore's real advantage lives

Past out_size=4,096, num_row_subchunks stays pinned at 4 and block size stays pinned at 1,024 rows — so a 64× larger input (out_size=262,144) just gets 64× more blocks, not bigger ones. That's exactly the regime SparseCore's pipelining is built for: at low window_fraction it beats dense there by up to 64×, and even at a full window (window_fraction=100%) it's still ≥2× faster at every out_size ≥ 65,536 tested. The unconditional choice is right at this end of the grid — it's only wrong at the two ends the real workload actually spends time in.

Cross-referencing all three findings against the 429,312 real calls logged in section 02: 10.19% of them — about 43,750 — landed on a shape where the kernel's unconditional choice measured slower than dense would have. Most of that, 6.98% of all traffic, is finding 01's clean, size-only story: calls at out_size ≤ 2,048 where dense wins no matter what the window looks like. The remaining 3.18% is finding 02's dominant-bucket tail — real calls at out_size=4,096 whose window happened to cross into a second pipeline block or further.

05 — Shipping It Behind a Flag

One Threshold, Checked Against Itself

The fix takes the clean half of the finding — the part that's true regardless of window — and ships only that: below out_size=2,048, route to a plain dense gather instead of the SparseCore kernel. 

def _fallback_implementation(x, indices):
    return x[indices]

# ...
use_dense = (
    sc_info is None
    or out_size <= envs.RAGGED_GATHER_V2_DENSE_FALLBACK_MAX_OUT_SIZE
)
if use_dense:
    return _fallback_implementation(x, indices)

Env-gated threshold, default matching the finding (RAGGED_GATHER_V2_DENSE_FALLBACK_MAX_OUT_SIZE=2048), 0 to disable and fall back to the old unconditional behavior for a direct A/B — no code branch to swap, no rebuild. It deliberately doesn't try to also reason about window: the out_size=4,096 tail is real (3.18% of traffic) but smaller and shaped differently, and a clean, size-only cutoff is easier to trust and to verify than one that also depends on a runtime window value.

Verification ran in two passes. First, the existing correctness suite — 49 cases across sizes, dtypes, and [start, end) windows — still passes, 49/49, and runs 2.6× faster, 124.07s → 47.2s, because the suite's small-out_size cases now skip SparseCore kernel compilation entirely — exactly the set the fix targets, confirming itself as a side effect. Second, toggling the flag against a live server and reading the diagnostic hook's own dispatch label back confirms the env-flag path reproduces the old hardcoded threshold exactly — dense_size_fallback below 2,048, sparse_core above it, same inputs either way.

A Real Fix, and Nothing to Show for It

Every metric sits inside run-to-run noise. Not a regression, not an improvement — indistinguishable. The arithmetic explains why before the load test even ran: roughly 43,750 calls paying SparseCore's fixed cost unnecessarily, saving on the order of 0.02 ms apiece on this grid, totals under a millisecond across the whole run — against a 41-second benchmark. ragged_gather_v2 is one small kernel sitting next to attention, the rest of the MoE expert matmul, KV-cache management, and scheduling. A sub-millisecond win anywhere in that stack was never going to move a stopwatch timing all of it.

SparseCore's overhead is fixed, not proportional — and a fixed cost only ever amortizes if the call is big enough to spread it over. Below 2,048 rows, no reshaping of the active window changes that; the dense fallback the kernel already contained was simply the right default all along for calls that size, and the fix is exactly as narrow as the evidence that supports it — a single out_size cutoff, nothing conditioned on window, verified against the same real traffic that motivated it. It didn't need an end-to-end number to be worth shipping, and the honest load test confirms it didn't get to claim one it hadn't earned, either.
