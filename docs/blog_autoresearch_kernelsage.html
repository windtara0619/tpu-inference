01 — The Problem

Fusing the Projections Into Attention

Why fuse q/k/v projection, norm, and RoPE into the kernel?

In a standard transformer serving stack, each layer runs the Q/K/V projections, RMS-norm, and rotary embedding as XLA ops outside the attention kernel. We set out to fuse all of it directly into our ragged paged attention (RPA) kernel, for two reasons:

  • Eliminate the DMA round-trips. The XLA path materializes Q (16.8 MB at 2048 tokens × 32 heads), K, and V (4.2 MB each) in HBM — only for the attention kernel to immediately read them back. The hidden states x are read from HBM once per projection on top of that. Fused, Q/K/V are born in VMEM and never touch HBM; x is read exactly once.
  • Fill the existing bubbles. The attention kernel already has idle MXU windows while it waits on KV-cache DMAs. Projection GEMMs are pure MXU work — in principle they can hide inside gaps the kernel is already paying for.

How we built the first version — and how slow it was

The v0 implementation was a textbook port. The kernel walks query tiles of bq_sz tokens; for each tile it double-buffers an x fetch from HBM, runs the Q projection GEMM on the MXU, then the Q norm + RoPE on the VPU, and stores the result to a double-buffered Q scratch. The KV side mirrored it: for each bkv_sz KV block, a second double-buffered x fetch, one big KV projection GEMM for the whole block, K norm + RoPE, bit-packing into the cache layout, and an async cache write-back. Attention then ran its usual flash QK/PV loops with double-buffered output sends. Everything that could be double-buffered, was.

And it didn't matter:

ConfigurationAttention kernelProj + norm + RoPEEffective total
Baseline (XLA external projections)253 µs~200 µs in XLA~453 µs
First fused version (v0)545 µsabsorbed545 µs

The fusion added 292 µs to absorb work XLA did in ~200 µs — slower than not fusing at all, even before counting the DMA traffic it saved. And a Pallas kernel is opaque: the profiler shows one 545 µs custom-call block and nothing inside it.

02 — See Inside

Drawing a Timeline for an Opaque Kernel

If the profiler can't see inside the kernel, rebuild the picture from parts. The auto-research engine benchmarks every unit op the kernel is made of, at the kernel's exact tile shapes — because GEMM efficiency at M=256 is not GEMM efficiency at M=64, and a norm over 32 heads is not a norm over 8.

The DMA model: solve for overhead and bandwidth

DMAs don't get benchmarked one by one — they get fitted. Every async copy obeys: 

latency  =  overhead  +  bytes / bandwidth

Measure the same copy at several sizes — a 0.33 MB x slice, a 1.3 MB x tile, a 4.2 MB cache block, the 31.4 MB weight matrix — and the two unknowns fall out of a least-squares fit: a fixed per-descriptor overhead ≈ 1 µs and an effective bandwidth ≈ 1.6 TB/s. From then on, the model predicts any DMA in the kernel from its byte count alone — including copies we haven't written yet, which is what makes roofline-checking a new idea nearly free.

From constants to swimlanes

A TPU core has three engines that run concurrently: the MXU (matrix), the VPU (vector), and the DMA engines. A kernel is fast exactly when all three are busy at once. A small event scheduler replays the kernel's program order — every GEMM, norm, and copy, with its true dependencies — using the fitted constants, and renders one swimlane per engine, one hoverable block per op.

The discipline that makes the diagram trustworthy: the model's total must match the measured total. Our v0 model summed to 545 µs against a 545 µs measurement. From that point on, every gap in the swimlanes was a real bubble with a name — and every model-vs-measurement mismatch was a hidden behavior worth digging into. Both kinds of signal ended up mattering.

03 — The Fix

Software Pipelining, Three Engines Deep

The diagram made the failure mode obvious: the engines were taking turns. The fix is classic software pipelining — run iteration t's vector work, iteration t+1's matrix work, and iteration t+2's DMA at the same time. The steady-state loop body became: 

# steady state for query tile t
start_fetch_x(t+2)          # DMA — two tiles ahead, into the third x slot
compute_q_proj(t+1)         # MXU — next tile's projection GEMM
compute_q_rope_norm(t)      # VPU — this tile's norm, hidden under the GEMM above
for kv_block j in tiles(t):
    prefetch_bkv(j+1)       # DMA — issued before waiting on block j
    attention_qk_pv(t, j)   # MXU — softmax acc rides the VPU under PV
send_output(t)              # DMA — async, double-buffered

DMA pipelining: why the buffer counts are what they are

  • x is triple-buffered. Slot t is still being read by the KV projection while slot t+1 feeds the Q GEMM and slot t+2 receives the prefetch. With only two slots, the t+2 fetch would overwrite data the KV GEMM is still reading — a write-after-read race. The third slot breaks it, and slot index is just t mod 3: no bookkeeping state.
  • Every prefetch is issued before the wait on the current block. That ordering is the whole trick of DMA pipelining: while attention chews on KV block j, block j+1 is already in flight. Each slot's lifetime is guarded by a DMA semaphore rather than a barrier — the consumer blocks only if the data genuinely isn't there yet.
  • MXU/VPU overlap comes from issue order. compute_q_proj(t+1) is issued before compute_q_rope_norm(t). They have no data dependency — one works on tile t+1's raw projection, the other on tile t's — so Mosaic's scoreboarding runs the 18.65 µs GEMM and the 6.35 µs norm concurrently. The norm disappears from the critical path entirely. This single reordering was worth −28 µs.

The KV recompute problem

One bubble was not a scheduling problem at all — and the way it surfaced is the point of the method. The unit math said the KV projection for 2048 tokens should cost ~28 µs of MXU time in total: every token's K/V computed once. But the ablation harness said the kernel was spending several times that on KV work, and the calibrated timeline couldn't be made to fit without it. The model and the silicon disagreed — so the engine went looking, and found that every query tile was recomputing K/V for every KV block it attended to. Query tile 5 computed blocks 0–1; tile 6 computed them again; the same projection ran up to num_bq times.

The fix restructured ownership: each KV row is computed exactly once, by the first query tile that covers it — straight from the x tile already resident in VMEM for the Q projection, which also killed the second x fetch — and written eagerly to the KV cache. Later query tiles re-read it as ordinary cached KV, and those reads are prefetched a block ahead, so they hide under attention instead of gating it.

04 — The Loop

An Engine That Checks Its Own Work

None of the above was a one-shot analysis. The auto-research engine wraps every change in the same verification machinery it used to find the problem — and each landed fix re-runs the loop, recalibrates the timeline, and re-ranks what's left.

Tests, written by the engine
14 kernel unit tests against a reference implementation — multi-sequence prefill, KV gaps, random pre-filled caches, tokens landing exactly on tile boundaries, partial decode batches — plus end-to-end serving tests. Every kernel rewrite must pass all of them before a benchmark is even attempted.
Benchmarks at two scales
A single-kernel microbenchmark (controlled shapes, profiled repetitions, device-time extracted from the trace) and full end-to-end serving runs under the production profiler — because a kernel win that doesn't survive the scheduler isn't a win.
Ablation harness
Patches any code region out of the kernel, measures 20 profiled repetitions, and auto-reverts the source. Run as a sweep, it prices every component of the fused kernel individually — GEMMs, norms, rotary, packing — and catches the components whose cost intuition gets wrong in both directions. Full results below.
XLA / Mosaic dumps
Compiled-HLO and Mosaic dumps for both the fused kernel and the baseline path it replaces. Reading what the compiler emits — rather than what the source says — reveals the optimizations worth stealing and the waste XLA silently inserts around the kernel boundary. Full findings below.

Ablation results

One sweep, run unattended (patch → compile → 20 profiled reps → auto-revert, sequentially on one TPU), attributes the entire fused kernel component by component. Full kernel: 424 µs at 2048 tokens:

The removable components sum to ~121 µs of the 176 µs fused delta; the rest is pipeline coupling, and the two GEMMs are already at the machine's roofline — meaning the remaining headroom is in scheduling, not arithmetic. And then there is the last row: deleting the Q norm made the kernel 65 µs slower. Its f32 intermediate and store pattern turn out to steer Mosaic's layout and pipelining for everything downstream. No intuition predicts that; the harness measured it in two minutes, and it saved us from "optimizing" a component that was actually load-bearing.

What the XLA dump showed

Dumping the compiled HLO for the baseline path (the same projection + norm + RoPE math, run as ordinary XLA ops) is how the engine learns what the compiler knows. The headline find, verbatim from the optimized module: 

;; XLA fuses the projection dot and the norm statistics into ONE pass —
;; the sum-of-squares comes out of the GEMM epilogue for free:
%fusion = (f32[2048,32], bf16[2048,32,128]) fusion(%w_q, %x), kind=kOutput
  %convolution = bf16[2048,32,128] convolution(%x, %w_q)   // Q projection
  %multiply    = f32[2048,32,128]  multiply(%conv, %conv)  // squares, in-register
  %reduce_sum  = f32[2048,32]      reduce(%multiply)       // RMS-norm statistics
  ROOT %tuple  = tuple(%reduce_sum, %convolution)
  • Norm statistics ride the GEMM epilogue. The projection output is squared and reduced while still hot, so the norm never re-reads 16.8 MB of Q from memory. Our kernel does GEMM → store → reload → norm: two VMEM round-trips XLA doesn't pay. This is the top item on the next-round roadmap.
  • sin/cos are computed once and shared. One sine/cosine table feeds both the Q-rope and K-rope fusions (the same tuple elements are consumed by both). Our kernel generates them twice — once per projection path.
  • Weights are prefetched across program boundaries. The dump shows copy-start(%w_q), cross_program_prefetch_index=0 — XLA starts staging the weight matrix into VMEM before the program even begins. The closest we can get in Pallas is the async prologue copy, issued as the kernel's first instruction.
  • The compound beats its parts. Measured on the same chip: XLA's proj + norm + RoPE takes 201.4 µs standalone, while the bare projection GEMMs alone take 234.1 µs — the epilogue fusion makes adding the norm faster than not. Our fused kernel's marginal cost for the same work is ~170 µs, so it now wins — but the dump says another ~30 µs is sitting in those two round-trips.

The dump also indicted the graph around the kernel: a [2560, 6144] weight concatenation re-materialized by three dynamic-update-slice fusions every layer, every step (~30 MB), and an 8.4 MB broadcast(0) zero-filling the kernel's donated output buffer per layer. Neither is visible from inside the kernel; both fell out of reading what XLA compiled. Their fixes are in the table below.

The three-step kernel eval

When asked "why is this kernel slow?", the engine runs a fixed protocol: (1) benchmark baseline vs. fused at matched shapes, (2) ablate every component to attribute the delta, and (3) compare against the roofline and the baseline's compiled dumps to find what the compiler knows that the kernel doesn't. The whole protocol runs unattended — sequentially on one TPU, kernel source auto-restored after every ablation.

It fixes its own bugs, and keeps digging

The recursion is what makes it an engine rather than a script. When the weight-fusion change broke model startup three different ways — a flax sharding constraint rejected the new parameter, then the checkpoint tracker flagged it as never loaded — the engine read each traceback, patched the loader, and re-ran until the end-to-end profile came back clean. When a hypothesis failed, it said so: guarding the kernel prologue was supposed to fix a 21 µs empty-kernel cost and measurably did nothing. Roofline arithmetic then named the real culprit — 21 µs ≈ 31.4 MB ÷ 1.6 TB/s, the weight matrix being block-copied into VMEM on every kernel entry, even empty ones — and the fix (an async prologue copy with a one-shot semaphore wait) took empty kernel calls from 21 µs to 0.4 µs.

Each answer produces the next question. Fixing the prefill pipeline exposed the weight-staging cost; fixing that exposed the decode kernel's prefetch serialization; fixing that put the decode kernel at the HBM roofline, where the only remaining lever is moving fewer bytes. The engine stops when the roofline says there's nothing left — not when a human gets tired.

05 — Beyond One Kernel

Everything Else the Loop Found

The 545 → 424 µs prefill story is the headline, but the same loop, left running, kept finding money on the table — inside the kernel, at the XLA↔Pallas boundary, and in the decode path:

The decode fix deserves a sentence: a race-condition guard added for prefill had been applied to the decode path too, forcing every sequence's KV-cache read to queue behind a cache write it never conflicted with. The timeline's DMA lane showed reads stacking up behind writes; the fix was three conditions, and it recovered 325 µs in a kernel that is memory-bound at 694 µs. The decode kernel now runs within 8% of the attention-only baseline while absorbing all of the projection work.

The fused prefill kernel now performs the projection + norm + RoPE work in ~170 µs of marginal kernel time — faster than the ~200 µs XLA spends on the same math standalone — while eliminating the Q/K/V HBM round-trips entirely. And the roadmap the engine produced for the next round is already ranked: fold the norm statistics into the GEMM epilogue the way XLA does, share sin/cos between Q and K, and hide the decode batch-head GEMM under the previous batch's DMA tail.

The meta-result matters more than the microseconds. Every technique in this post — unit-op fitting, timeline reconstruction, bubble detection, software pipelining, ablation, compiler-dump archaeology — ran as one autonomous loop. Point it at a kernel, and it comes back with the diagram, the diagnosis, the patch, and the receipts.
