TPU SparseCore · MoE Optimization

SparseCore
in MoE

Google's TPU includes a hardware unit called SparseCore, originally designed for embedding lookups in recommendation models — workloads that need to fetch scattered rows from enormous tables at high speed. Serving large Mixture-of-Experts models on TPU creates a structurally similar problem: routing tokens to their selected experts also means gathering scattered data based on a dynamic index. Teams are now reaching for SparseCore for this new job — but "the hardware fits the problem" and "the hardware is well-tuned for the problem" are not the same thing. This post documents what a first careful look under real production traffic found: what was over-counted, what was actually broken, what fixes worked, and where the current limits sit.

01 — Background

Why SparseCore, and Why Now

SparseCore is a hardware unit built into Google TPUs specifically to accelerate indirect memory access — operations where you don't read data sequentially but instead follow a dynamic index to gather scattered rows from a large table. That pattern is the core operation in recommendation models (look up an embedding for each item in a user's history), which is what SparseCore was originally designed for.

Where the two kernels appear in a MoE forward pass

In a model like Qwen3-30B-A3B, every transformer layer contains a MoE block. Each token goes through it in five steps, and SparseCore is responsible for exactly two of them.

  1. Route. A small router network scores each token against all 128 experts and picks the top-k (here, top-8). The output is a list of (token, expert, weight) assignments — a different list for every request in the batch.
  2. Dispatch — ragged_gather. The experts are spread across 8 chips (16 experts per chip). Tokens first cross the chip interconnect to land on the right chip. Then ragged_gather runs on SparseCore: it reads each incoming token embedding from wherever it sits in memory and writes it into the slot each local expert is expecting. The index is the router's assignment list — different every step, never a fixed stride. Different experts receive wildly different numbers of tokens depending on what the router decided, which is what makes the access pattern "ragged."
  3. Compute. Each chip runs its local experts as a batched matrix multiply on the tokens now sitting in expert order. This is TensorCore work — SparseCore is idle here.
  4. Combine — ragged_gather_reduce. Each token was sent to multiple experts; now their outputs need to be merged back into a single vector per token. ragged_gather_reduce runs on SparseCore: it reads the per-expert output for each (token, expert) assignment, multiplies by the router weight for that pair, and accumulates the results — a weighted sum — into the output slot for that token. Again, the access pattern is driven by the router's dynamic assignment, not a fixed layout.
  5. Return. Combined token outputs cross the interconnect back to their home chips. The MoE block is done.

SparseCore's 8-lane parallel-DMA architecture is a natural fit for steps 2 and 4 — they are exactly the indirect scatter-gather problem it was built for. But "the hardware fits the problem" and "the hardware is well-tuned for the problem" are not the same thing. SparseCore has existed for years in the embedding-lookup context; using it for MoE token routing is recent, and the operational profile is different enough that assumptions from one domain don't transfer automatically. This post documents what a systematic look at both kernels under real production traffic found.

The investigation covers four optimizations — two per kernel. Each gets the same treatment: how the problem was detected, how the fix was found, how it was verified against data that reflects real traffic distributions, and what it changed end to end. Two additional attempts that turned out to be dead ends are documented explicitly — knowing a lever doesn't exist is as useful as knowing one does.

When SparseCore Is the Wrong Tool for the Job

Both kernels have a TensorCore fallback path — a plain dense gather or reduce that runs on TensorCore instead of SparseCore. Whether and when to take it is a dispatch decision. The two kernels started from very different places: ragged_gather had no dispatch condition at all (always SparseCore), while ragged_gather_reduce had a size-only condition. Sweeping both against their TensorCore fallback across a range of real call shapes shows neither setting was right.

01

The threshold is correct only at ~10% valid rows — move to 20% and the crossover shifts past 3×

At 10% valid, SparseCore wins from just above the threshold (1.1×) onward. At 20%, it doesn't win until beyond 2× the threshold. At 40%+, SparseCore needs to be 3×+ the threshold before it catches up. The size-only criterion gets this right only in the sparsest slice of traffic.

02

Past ~3× the threshold, the crossover settles near 44–49% valid — independent of size

For every size from 3× to 16×, SparseCore wins at 40% valid and loses at 50% valid — the same bracket across a 5.3× range in raw size. The true crossover is roughly ~47% valid rows for large inputs, consistent with SparseCore's per-call cost becoming linear in valid-row count once the input is large enough to amortize start-up.

03

All 126 misfires over-commit to SparseCore — not one goes the other way

In 260 cells, the criterion was wrong 126 times. Every single misfire chose SparseCore when TensorCore was faster — worst case 4.68× the optimal time. The asymmetry points clearly at what a better criterion would need to add: a validity check, not a size adjustment.

Why this hasn't caused a visible problem yet: a live server trace checked which fraction of real ragged_gather_reduce calls actually land in the misfire region. The dominant production shape runs at low valid-row fractions — well below the 47% crossover — so the size-only criterion happens to pick correctly for most real traffic, even though it's wrong for a large portion of the parameter space. The opportunity is to make the criterion correct by construction, not just accidentally correct for today's traffic distribution.

03 — Tiling Tuning

Chunk Size, Pipeline Restarts, and Hard Constraints

Both kernels process their work in fixed-size tiles. The tile size controls how often the SparseCore pipeline has to drain and restart — a real source of idle time on every chunk boundary. We tuned this parameter for both kernels. The outcomes were different.

ragged_gather shipped

Detect

A profiling run reported ragged_gather spending roughly 64% of its on-device time stalled waiting on data. The actual issue is a structural property of how SparseCore pipelines work: the internal pipeline must fully drain and restart at each chunk boundary, leaving the hardware idle while the next chunk's data arrives. Measuring those waits accurately requires a self-time reconstruction — crediting each unit of time to exactly one leaf event, without double-counting nested spans. Over all 2,208 real kernel instances in the trace, no definition reached 64%:

How stall was measuredValue
Input-wait events only / total on-device time12.6%
Input-wait / compute time17.1%
All wait events (input + output + finalize) / total16.9%
Everything outside active compute / total (broadest reading)26.4%
Highest single instance (any definition)54.7%

None of these reach 64%, by a wide margin. It's not clear whether that figure came from a different capture, a different tool, or a mix-up with an unrelated 64× SparseCore-vs-dense speedup figure from an earlier investigation. The investigation moved forward calibrated to the real, measured 26.4%.

Solve

Deeper prefetching — keeping the next chunk's data arriving while the current chunk computes — hit two hard framework limits and was ruled out. Instead, the fix reduces how often the pipeline restarts at all by doubling the chunk size. Larger chunks mean fewer restart boundaries per call, but chunk size is static at compile time: for a small live window, the extra padding iterations still run regardless. A log-spaced sweep makes the trade-off explicit:

A second independent trace (2,592 instances) confirmed the range: 28.1% broadest definition, max single occurrence 34.3%. Re-running cap=4 vs cap=8 on fresh trace pairs:

E2E

Whole-model device timeline (one large prefill + one decode step): 1.637s vs. 1.651s — flat, within single-iteration noise. ragged_gather isn't on the critical path at this workload; a real ~10% reduction in its own on-device time doesn't move overall latency here.

ragged_gather_reduce dead end

ragged_gather_reduce is the second half of MoE token routing — after expert computation, it gathers each token's expert outputs, weights them by router probability, and sums them back to one vector per token. The same tiling question applies: can chunk size or the row/column partition split be tuned?

Attempt 1 — adjust the row/column split

Unlike ragged_gather, ragged_gather_reduce tiles work across both rows and columns simultaneously — the weighted sum needs to accumulate partial results that don't fit in on-chip memory at once. Sweeping all values at the real production shape:

Column partitionsRow partitionsResult
132fails — exceeds hardware lane count
216fails — same constraint
48only value that compiles
84fails — on-chip memory overflow
162fails — same, worse

Two hard constraints squeeze from opposite sides: the hardware lane count forces a minimum on column partitions, the on-chip memory budget forces a maximum. They meet at exactly one point. No lever to pull.

Attempt 2 — apply the same chunk-size fix

The same chunk-size increase was attempted for ragged_gather_reduce. Here it doesn't compile at all: the kernel carries more per-chunk bookkeeping state (sort permutation, destination indices, weights, carry values for the segmented reduction) and hits a hard on-chip register-file ceiling with a single word of margin.

Off by a single word. Both attempts are documented dead ends, not silently dropped — knowing a lever doesn't exist is itself a finding. It directs the next investigation toward the actual bottleneck rather than a parameter space that's fully constrained.

04 — ep_run_kernel Load Imbalance
shipped

Static Partitions, Skewed Routing

With tiling fully constrained for ragged_gather_reduce, the investigation turned to a different question: are all eight partitions actually doing equal work? The answer, measured from real traffic, is no — by a wide margin.

Detect

An instrumented logging path was added to read the real valid-row count on every production call. The preprocessing step splits each shard's local-expert token range into 8 equal-sized contiguous slices — but the valid-row bitmask is indexed in token-major order, so a contiguous slice is a contiguous batch-position range, not an expert-sorted one. Real MoE routing correlates with batch position: one request routing heavily toward a shard's local experts, another barely touching them, lands as one overloaded partition and one idle one. Measured from 1,920 real production calls:

Per-shard valid-row count (n=1,920)Value
Naïve estimate (tokens × top-k / devices)32,768
Real stdev22,998.6 (70% relative)
p10 / p50 / p903,609 / 31,919 / 65,536
Min / max0 / 163,840
Shard-instances at exactly zero valid rows6.6% (127 / 1,920)
Shard-instances > 2× naïve estimate6.6% (max single case: 5.0×)
Shard-instances < 0.5× naïve estimate17.7%

Ruled out: a statistical sizing formula. A simple statistical formula (tokens × top-k / devices ± margin) fails on two counts — the naïve model overshoots the real mean by 2–35× depending on the call, and its predicted spread is the opposite shape of what's real: the formula predicts a narrow band, the measurements show one where standard deviation exceeds the mean. No closed-form margin describes a distribution that swings from 0 to 5× on the same call, same layer, same config.

Solve

The preprocessing step gains an alternate mode: instead of splitting the row index space into contiguous blocks (giving one block the hot range, another nothing), it interleaves token groups across all eight partitions by round-robin rank. Each output token's top-k choices are kept together and assigned to whichever partition its sequential rank falls into — 0, 1, 2, ..., 7, 0, 1, ... — rather than by contiguous index range. A contiguous run of valid rows, wherever it falls in the batch, now lands roughly one-eighth in every partition instead of concentrating in one or two. Shipped as an opt-in feature flag, defaulting to the previous behavior.

Verify

The full test suite for ragged_gather_reduce — 54 cases, exact numerical comparison against a reference implementation — passes with the flag both off and on, bit-identical. Performance A/B at the real production shape with a single contiguous valid span (mimicking the real skew):

What's real and consistent: TTFT improves by an amount that scales with how prefill-dominated the workload is — 1–4% in decode-heavy shapes, 5–8% in prefill-heavy ones. Decode is neutral, not regressed.

An open question, not a settled story. Section 05's own isolated benchmark for the interleave fix alone, at this exact 1,024/1,024 shape, measured P99 TTFT at −1.0% — decode-heavy and close to flat. This session's fresh run of all four SparseCore flags together, same shape, measured −65.3%. Those two numbers are hard to reconcile from the isolated data alone: either the four flags interact non-additively at this concurrency (512, uncapped request rate), or something about this session's specific load-generator settings (uncapped request rate, fixed prompt and output length) produces queuing behavior the original single-flag runs didn't hit. Consistent with every self-correction already in this post: the honest move is to flag the gap rather than construct a causal story the isolated benchmarks don't support. Isolating which of the four flags — or which pairwise interaction — drives the bulk of the bundled P99 TTFT win is the natural next benchmark, not yet run.

What both bundles agree on, without qualification: every metric moved the right direction, in both runs, on a real live server. SparseCore's four flags alone are worth roughly 58% of the bundled throughput win and 93% of the bundled P99 TTFT win — the two dead ends in section 04 didn't cost anything (they were never shipped), and the two shipped fixes carry almost the whole result.

Four flags, two kernels, two dead ends documented instead of hidden, and three separate self-corrections that survived into this post instead of being quietly dropped. Detect off a real trace or a real logging hook, never a synthetic guess. Solve with a grid swept across the actual shapes and distributions production logs — not a plausible-looking range. Verify against data built to mimic that same real distribution, and re-run the comparison when a number doesn't add up, including numbers that already shipped. Report the end-to-end result even when it's a wash, and report the gap between an isolated benchmark and a bundled one honestly when the two don't agree. That discipline is worth more than any single percentage in this post.
