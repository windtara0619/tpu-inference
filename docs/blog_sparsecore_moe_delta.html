01 — The Ask

Two Kernels, One Restart-Bound Question

tpu_inference dispatches two SparseCore Pallas kernels on the MoE path, once per layer, under expert parallelism:

  • ragged_gather_v2 — permutes hidden_states into expert-sorted order before the expert matmul (the dispatch gather).
  • ragged_gather_reduce_v2 — gathers by topk_argsort_revert_indices, weights, and segmented-reduces topk rows back into one output token per row (the combine step).

A ten-commit investigation touched seven env-gated flags across MoE dispatch; only four actually run inside these two kernels — RAGGED_GATHER_V2_DENSE_FALLBACK_MAX_OUT_SIZE, RAGGED_GATHER_V2_MAX_NUM_ROW_SUBCHUNKS, RAGGED_GATHER_REDUCE_V2_MAX_NUM_ROW_SUBCHUNKS, and RAGGED_GATHER_REDUCE_V2_INTERLEAVE_ROW_PARTITIONS. This post is only about those four — two shipped fixes per kernel, one of the four a documented dead end. Each one gets the same four-part treatment: how the problem was detected, how the fix was found, how it was verified, and what it did end to end.

02 — ragged_gather_v2 · Fix 1

An Unconditional Choice, Checked Against Itself

ragged_gather_v2's dispatch logic is one branch: if SparseCore hardware exists, always use it, regardless of call size. 

sc_info = pltpu.get_tpu_info().sparse_core
if sc_info is None:
    return x[indices]   # only for missing hardware, never for speed
# otherwise: always SparseCore, no matter how small the call

Detect

A SparseCore kernel invocation carries real fixed cost before it moves a single byte — DMA descriptor construction, semaphore handshakes, pipeline warm-up — and that cost doesn't shrink with call size. If a gather is small enough, fixed cost can outweigh anything SparseCore's throughput buys back. Rather than guess where that line sits, the kernel was instrumented directly: MOE_LOG_RAGGED_GATHER_V2_STATS, a diagnostic hook off by default, logs out_size, hidden_size, dtype, and the [start, end) window on every real call. With it on, a live vllm serve of Qwen3-30B-A3B (TP=8, EP=8, dp_attention sharded 8-way, chunked prefill, async scheduling) was driven by vllm bench serve at 512 concurrent requests, 1,024-token prompts and generations.

429,312 real calls logged before a single synthetic benchmark ran. Every one carried hidden_size=2,048, bfloat16, and out_size landed on one of exactly 12 XLA-compiled bucket sizes — 90.79% of calls at out_size=4,096 alone. The same hook logged each call's active window as a fraction of out_size: mean 12.5%, median 11.7%, p99 33.4%. Two numbers now anchor the sweep exactly to production — which 12 sizes to test, and what window range to test them across.

Solve

The engine built a full grid: the same 12 real out_size buckets crossed with 11 window_fraction steps from 2% to 100% — 132 cells, hidden_size=2,048 and bfloat16 fixed at the real values, on the same v6e-8 the traffic capture ran on. Every cell timed the SparseCore kernel and the dense gather back to back on identical tensors — 30 timed iterations per cell (200 for the dominant out_size=4,096 row, to resolve it past measurement noise).

01

Below out_size=2,048, dense wins every cell — window never matters

At these sizes the pipeline's block size already exceeds out_size itself, so the kernel can never use more than one block no matter where the window ends. Dense wins by 1.7×–2.4× regardless, purely on fixed per-call overhead a single block can't amortize.

02

At the dominant bucket, out_size=4,096, the crossover is a hard step at window=1,024

The dense÷SparseCore ratio sits flat at ≈1.00× for every window ≤ 1,024 (true parity, one block), then drops to a flat 0.72× the instant the window crosses into a second block — 0.56× at a third, 0.46× at a fourth. No gradual crossing, only edges.

03

Past out_size=4,096, block size stops scaling — that's where SparseCore actually wins big

num_row_subchunks stays pinned at 4 past this point, so a 64× larger input just gets 64× more blocks. That's exactly the pipelining regime SparseCore is built for — up to 64× faster at low window fractions, still ≥2× at a full window for every out_size ≥ 65,536.

Cross-referenced against the 429,312 real calls: 10.19% of them — about 43,750 calls — landed on a shape where the kernel's unconditional choice measured slower than dense would have. 6.98% of all traffic is finding 01's clean story (size alone); the remaining 3.18% is finding 02's dominant-bucket tail.

The fix ships only the clean half — the part true regardless of window: below out_size=2,048, route to a plain dense gather. 

def _fallback_implementation(x, indices):
    return x[indices]

use_dense = (
    sc_info is None
    or out_size <= envs.RAGGED_GATHER_V2_DENSE_FALLBACK_MAX_OUT_SIZE
)
if use_dense:
    return _fallback_implementation(x, indices)

Env-gated (RAGGED_GATHER_V2_DENSE_FALLBACK_MAX_OUT_SIZE=2048 default, 0 disables), and deliberately size-only — the smaller window-tail fix (3.18% of traffic) was left out because a clean cutoff is easier to trust and verify than one that also depends on a runtime window value.

Verify

Two passes. First, the existing correctness suite — 49 cases across sizes, dtypes, and windows — still passes, 49/49, and runs 2.6× faster (124.07s → 47.2s), because the suite's small-out_size cases now skip SparseCore compilation entirely — the exact set the fix targets, confirming itself as a side effect. Second, toggling the flag against a live server and reading the diagnostic hook's own dispatch label back confirms the env-flag path reproduces the old hardcoded threshold exactly: dense_size_fallback below 2,048, sparse_core above it, same inputs either way.

E2E

512 concurrent requests, decode-heavy shape (128-token prompts, 1,024-token generations — the config that pushes the most steps through this exact path):

Every metric sits inside run-to-run noise — not a regression, not an improvement. ~43,750 calls paying an unnecessary fixed cost, saving on the order of 0.02 ms apiece, totals under a millisecond across a 41-second run. ragged_gather_v2 is one small kernel next to attention, the expert matmul, KV-cache management, and scheduling — a sub-millisecond win anywhere in that stack was never going to move a stopwatch timing all of it. The fix is exactly as narrow as the evidence that supports it, and the honest load test confirms it didn't get to claim a win it hadn't earned.

03 — ragged_gather_v2 · Fix 2

64% Reported, 26.4% Real

Detect

A profiling run of a real serving config — TP=8, expert-parallel, attn_dp_size=8, batch-size=8 input-len=4096 output-len=2, via examples/tpu_profiling.py — reported ragged_gather_v2 spending roughly 64% of its on-device time stalled inside fused_moe_gmm. The first reproduction attempt targeted the wrong mechanism entirely — a mismatch between the padded out_size and the real [start, end) window, the same axis Fix 1 already gates on. It reproduced a real slowdown on synthetic shapes, but it wasn't what the profile was pointing at.

The actual target was the kernel's own inner nested pipeline (ragged_gather_v2.py:203), the pltpu.emit_pipeline call the file's own TODO already flags: it "creates a pipeline bubble (DMA wait) when the inner pipeline empties and restarts with new indices." The nested pipeline emits real, named stage events on every SparseCore subcore track — ep_initialize_0 → ep_copy_in → ep_wait_in → ep_run_kernel → ep_copy_out — where ep_wait_in is the literal DMA-wait bubble: the subcore blocked on the next gathered row-subchunk's input DMA.

Summing these tags naively double-counts — an outer ep_run_kernel can wrap a nested one, and a different kernel instance can even nest inside another's span via SparseCore's async dispatch. The fix: a stack-based self-time reconstruction (duration minus direct children's duration, so every picosecond attributes to exactly one leaf event) over an overlap-safe union of each instance's span. Run against all 2,208 real sc_ragged_gather_v2.* instances in the trace, no definition built from these tags reached 64%:

DefinitionValue
ep_wait_in / total on-device time12.6%
ep_wait_in / ep_run_kernel17.1%
(ep_wait_in+ep_wait_out+ep_finalize) / total16.9%
total − ep_run_kernel / total (broadest reading)26.4%
highest single instance (any definition)54.7%

None of these reach 64%, by a wide margin. It's not clear whether that figure came from a different capture, a different tool (op-stats' dedicated hardware stall counters exist in the schema but weren't populated in this capture), or a mix-up with an unrelated 64× SparseCore-vs-dense speedup figure from an earlier, separate investigation at this exact shape. The investigation moved forward calibrated to the real, measured 26.4% instead of chasing the original number further.

Solve

The natural first move — give the nested pipeline more buffers so it can prefetch further ahead — hit two hard limits in the installed Pallas, not in this repo's code:

Multi-buffered indirect input
in_specs uses pl.Indirect(...) — each block's index is a vector of gathered rows, not one scalar. Setting buffer_count=3 on it crashes: TypeError: Pred must be a scalar, got bool[8]. Two call sites in Pallas's pipeline emitter don't special-case indirect refs the way three sibling methods do — confirmed with use_lookahead=True too, same crash, different call site.
Multi-buffered output
Moving buffering to out_specs sidesteps the bug above, but buffer_count=3 hits an explicit, by-design limit: NotImplementedError: Buffer count >2 not supported for output buffered refs. Only input unbuffered, output buffer_count=2 actually runs — verified correct, but it didn't move the stall numbers meaningfully.

With multi-buffering blocked upstream, the fix instead reduces how often the inner pipeline restarts at all. Raising num_row_subchunks's cap from 4 to 8 doubles block_size — fewer restarts per call, amortizing more of the fixed ramp-up cost — but the inner pipeline's grid is a static shape unrelated to how much of [start, end) is real data. For a small window, doubling the cap just doubles the number of mostly-padding grid steps that still have to run. A log-spaced sweep across window sizes, both caps, makes the trade-off explicit:

Window (rows)cap=4 (µs)cap=8 (µs)Speedup

1,024526.2903.10.58×

The crossover falls exactly at 2,048 — that's cap=8's own block_size (row_subchunk_size(8) × 8 × num_cores(32)). Below it, num_blocks = cdiv(window, block_size) is already 1 under both caps, so cap=8's extra grid steps are pure waste with nothing to offset them — flat ~0.58× loss across the whole 8–1,024 range instead of tapering off. Above it, num_blocks starts actually dropping under cap=8, and the restart-amortization benefit takes over.

Real EP-permute traffic mixes window sizes — per-instance durations in the profiled trace ranged ~16µs to ~984µs at the cap=4 baseline. Raising the cap unconditionally risks trading a win on hot-expert calls for a real ~1.7× regression on cold-expert/small-window calls, which the trace suggests are common. That's why the default stayed at 4: RAGGED_GATHER_V2_MAX_NUM_ROW_SUBCHUNKS, an A/B knob, not a silent behavior change.

Verify

Rather than approximate the stall with a synthetic dense-gather comparison, tests/kernels/ragged_gather_v2_stall_test.py captures a live jax.profiler.trace at the real sc_ragged_gather_v2.80 shape (out_size=262144, hidden_size=2048, in_size=32768, bf16) — mimicking the exact shape and data distribution the production trace logged — and runs the same self-time, overlap-safe reconstruction used to derive the 26.4% number, so the assertion checks the same thing the real trace was read for, not a stand-in.

On this session's own hardware (a single v6e-1 chip, vs. the profiled 8-chip pod), the full-window case landed at 26.39% total overhead — within 0.01 points of the real trace's 26.4%. A different chip, a different topology, the same mechanism, the same number to two decimal places — the signal this reproduction was built correctly, not just plausibly.

A second, independent live trace (cap=4, 2,592 real instances) confirmed the range rather than drifting from it: 28.1% by the broadest definition (vs. 26.4% originally), max single occurrence 34.3% (0 of 2,592 exceeding 50%). Re-running the cap=8 mitigation on fresh cap=4/cap=8 trace pairs at the full window:

Metric (gather-scoped)cap=4cap=8Δ
Total SparseCore time under gather1,145.5 ms1,028.3 ms−10.2%
ep_wait_in203.0 ms (17.72%)113.9 ms (11.08%)−44%

A stricter, profiler-label-independent check — each ep_run_kernel's own self-time distribution, since a blocked multi-buffering fix means some DMA-wait can get absorbed inside a run span instead of tagged separately — tells the same story from a different angle: under cap=4 the bulk of calls are tight, but a genuine outlier tail runs up to 90.4µs (≈36× median); under cap=8, zero calls exceed 2× median anywhere in the distribution, and the max drops 96.6% to 3.1µs. By this definition the fix doesn't just shrink the stall, it removes it.

E2E

Whole-model device timeline for the exact profiled step (TensorCore + SparseCore combined busy window): 1.637s (cap=4) vs. 1.651s (cap=8) — flat, within single-iteration noise. At this workload (one large prefill + one decode step), ragged_gather_v2 isn't on the step's critical path, so a real, independently-confirmed ~10% reduction in its own on-device time doesn't move overall latency here. It may matter more at configs where MoE-permute is a bigger share of the critical path — larger batch/expert counts, decode-heavy workloads. (A naïve first pass — min/max timestamp across the entire trace file — gave a false −32.7%; that was /host:CPU background threads parked in unrelated waits, not device work, and had to be excluded.)

04 — ragged_gather_reduce_v2 · Same Lever?
dead end

The Same Question, a Kernel With No Slack

ragged_gather_reduce_v2 is the combine step. Unlike ragged_gather_v2 it already splits both row and column axes across cores. Before looking for a different fix, the natural question: is that split tunable the same way num_row_subchunks turned out to be for the gather kernel?

Detect

A direct, profiler-grounded bandwidth fit (single SparseCore lane vs. full 32-lane chip, live-traced elapsed device span) reproduces the same hardware picture found for ragged_gather_v2: 19.160 GB/s per lane, R²=1.000000, scaling to 593.9 GB/s at full occupancy — 96.9% of the naive 32× prediction, the same ~3% sub-linear falloff measured for the other kernel. No lane contention, no headroom to reclaim by concentrating work on fewer cores.

Solve — attempt 1: sweep the row/column split

num_column_partitionsnum_row_partitionsResult
132fails — exceeds SIMD lane count (8)
216fails — same constraint
48only value that compiles
84fails — VMEM allocation overflow
162fails — same, worse

At the real production shape, num_column_partitions=4 isn't tuned — it's the only value that compiles. Two hard constraints converge on it from opposite directions: num_row_partitions ≤ num_simd_lanes(8) forces ncp≥4, while a per-partition VMEM buffer blowing the 256KB budget once num_row_partitions<8 forces ncp≤4. No slack to search — unlike ragged_gather_v2's row split, this axis has nothing to tune.

Solve — attempt 2: mirror the subchunk cap anyway

A RAGGED_GATHER_REDUCE_V2_MAX_NUM_ROW_SUBCHUNKS knob was added, mirroring the gather kernel's fix (_calculate_row_tiling had the cap hardcoded to 4, derived from the static padded input_size rather than any real per-partition valid count — so it was always saturated regardless of real work). Raising it to 8 doesn't trade off against small windows the way it did for the gather kernel — it doesn't compile at all: 

error: 'memref.alloca' op E3000: CompileTimeSparseCoreAllocationFailure:
current allocation offset upper bound (28 words) exceeds the legitimate
user allocatable offset upper bound (27 words) in memory space sflag_tile
when allocating 2 words

Off by a single word. This kernel's nested row/col pipeline carries more per-row-subchunk state than ragged_gather_v2's plain gather — segmented-reduction bookkeeping: sort permutation, destination indices, weights, carry values — so it hits a hard SparseCore scalar-flag allocator ceiling the simpler kernel never approached. cap=4 is the ceiling here, not a choice. Both attempts are documented dead ends, not silently dropped — knowing a lever doesn't exist is itself a finding.

05 — ragged_gather_reduce_v2 · The Real Fix
shipped

Static Partitions, Skewed Routing

Detect

With both split axes closed off, a debug hook — MOE_LOG_COMBINE_VALID_ROWS_STATS, gated in fused_moe_gmm.py — was added to read the real, ground-truth valid-row count directly from jnp.sum(mask) on every real production call, rather than estimating it from trace timing. _preprocess splits each shard's local-expert token range into num_row_partitions=8 equal-sized contiguous index-range slices. But valid_rows_mask is indexed in token-major order — the segmented reduce sums consecutive topk entries per output token — so a contiguous partition slice is a contiguous batch-position range, not an expert-sorted one. Real MoE routing correlates with token/batch position: one request routing heavily toward this shard's local experts, another barely touching them, lands as one overloaded partition and one idle one.

Real per-shard valid-row count (n=1,920, production scale)Value
Naive estimate (num_tokens×topk/devices)32,768
Real stdev22,998.6 (70% relative)
Min / max0 / 163,840
Shard-instances at exactly zero valid rows6.6% (127 / 1,920)

Ruled out: a statistical sizing formula. A num_tokens×topk/devices ± σ formula was tested directly against this ground truth and fails on two counts — the naive uniform-random model overshoots the real mean by 2–35× depending on the call, and its predicted spread (std≈60, tiny relative to the mean) is the opposite shape of what's real (std > mean). No closed-form margin describes a distribution that swings from 0 to 5× on the same call, same layer family, same config. A narrower idea — skip the inner pipeline's trailing, padding-only subchunks in a partition's last block — was modeled directly against the trace too: real, but only ~1.80% aggregate, small enough to deprioritize against fixing the partitioning itself.

Solve

_preprocess gains an alternate path: instead of valid_rows_mask.reshape(num_row_partitions, -1) (contiguous blocks), it reshapes to (token_groups_per_partition, num_row_partitions, reduce_group_size), transposes, and flattens — assigning token-group t (one output token's topk choices, kept together) to partition t % num_row_partitions by round-robin rank instead of index range. A contiguous run of L valid rows, wherever it falls, now lands ~L/8 in every partition instead of concentrating in one or two. The stable sort-by-validity and the rest of the kernel are untouched — only which original row a given partition slot maps back to changes.

Landed behind RAGGED_GATHER_REDUCE_V2_INTERLEAVE_ROW_PARTITIONS, default false.

Verify

Correctness first: the full ragged_gather_reduce_v2_test.py suite — 54 cases, exact numerical comparison against a reference implementation — passes with the flag both off and on, and a direct output comparison between old and new preprocessing on the same kernel, same inputs, is bit-identical.

Performance verification used the same principle as the gather kernel's stall test — build synthetic input that mimics the real logged distribution, not an arbitrary one. A synthetic A/B (single contiguous valid span, matching the real skew pattern from the table above, at the real production shape) isolates the fix's effect:

A self-correction worth keeping. An earlier version of this result claimed 3.9×–7.7× speedups, but no benchmark script backing that table existed anywhere in the repo. A follow-up session rebuilt the benchmark from scratch against the real kernel — bit-identical output confirmed independently — and found the same qualitative pattern (old plateaus once the hot span fills a full partition-width; new scales roughly linearly since it's balanced from the start) but roughly half the magnitude, 1.6×–5.4× at every span size tested. The table above is the reproduced numbers, not the original claim.

Another self-correction. An earlier pass at this section, from one shape only, reported a 73.2% P99 TTFT improvement with flat mean/median — a dramatic isolated-tail-fix story. It doesn't hold. Across all three shapes, P99 TTFT moves by roughly the same magnitude as mean/median TTFT, never dramatically more — no evidence for an isolated-tail mechanism. What's real and consistent instead: TTFT improves in every shape by an amount that scales with how prefill-dominated the workload is — roughly 1–4% when a long decode phase dominates (1,024/1,024), 5–8% when prefill dominates (4,096/2 and 8,192/1). Decode itself is neutral, not regressed — flat within noise on the one shape with a genuine steady-state decode phase. Each shape here is one run (--request-rate inf, shared pod), so individual percentages carry a few points of noise; the consistent direction across three structurally different shapes is the stronger signal.

06 — End to End, This Session

What All Four Flags Add Up To, Measured Fresh

Qwen3-30B-A3B · TP=8 + expert-parallel · dp_attention=8 · bfloat16 · TPU v6e-8 · 512 concurrent requests, 512 prompts, fixed 1,024-in/1,024-out

An open question, not a settled story. Section 05's own isolated benchmark for the interleave fix alone, at this exact 1,024/1,024 shape, measured P99 TTFT at −1.0% — decode-heavy and close to flat. This session's fresh run of all four SparseCore flags together, same shape, measured −65.3%. Those two numbers are hard to reconcile from the isolated data alone: either the four flags interact non-additively at this concurrency (512, uncapped request rate), or something about this session's specific load-generator settings (--request-rate inf, --random-range-ratio 0.0 for a hard-fixed length) produces queuing behavior the original single-flag runs didn't hit. Consistent with every self-correction already in this post: the honest move is to flag the gap rather than construct a causal story the isolated benchmarks don't support. Isolating which of the four flags — or which pairwise interaction — drives the bulk of the bundled P99 TTFT win is the natural next benchmark, not yet run.

What both bundles agree on, without qualification: every metric moved the right direction, in both runs, on a real live server. SparseCore's four flags alone are worth roughly 58% of the bundled throughput win and 93% of the bundled P99 TTFT win — the two dead ends in section 04 didn't cost anything (they were never shipped), and the two shipped fixes carry almost the whole result.

Four flags, two kernels, two dead ends documented instead of hidden, and three separate self-corrections that survived into this post instead of being quietly dropped. Detect off a real trace or a real logging hook, never a synthetic guess. Solve with a grid swept across the actual shapes and distributions production logs — not a plausible-looking range. Verify against data built to mimic that same real distribution, and re-run the comparison when a number doesn't add up, including numbers that already shipped. Report the end-to-end result even when it's a wash, and report the gap between an isolated benchmark and a bundled one honestly when the two don't agree. That discipline is worth more than any single percentage in this post.
