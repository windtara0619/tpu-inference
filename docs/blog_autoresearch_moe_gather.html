01 — The Ask

Where Is the Time Actually Going?

The baseline

Model: Qwen3-30B-A3B — 48 layers, 2048 hidden, 32 query heads / 4 KV heads (GQA), 128 experts per layer with 8 active per token. Pulled straight from the model's own config.json, not the marketing name, the parameter split looks like this:

ComponentTotal (all 128 experts)Active (8/token)
MoE expert FFN29.0B (95.0%)1.81B (54.0%)
Attention0.91B (3.0%)0.91B (27.0%)
Embedding + LM head0.62B (2.0%)0.62B (18.6%)
Total30.5B3.35B

By stored weight this model is 95% MoE — attention is a rounding error next to 128 experts × 48 layers. But only 8 of those 128 experts fire per token, so active compute per forward pass is a much closer split: roughly 54% MoE, 27% attention, 19% embedding. That gap — 95% of the weights, 8 experts actually touched — is exactly why routing costs so much here. Sparsity doesn't shrink the dispatch problem, it creates it: a dense FFN needs no routing at all, but a sparse one needs every single token sorted, counted, and gathered to the right 8-of-128 before any expert math happens. That dispatch work is what the three gathers in section 02 are doing.

The request that started this was a real serving command: a hybrid sharding scheme — 8-way Attention Batch Sharding (data parallelism, DP=8) combined with 8-way Expert Parallelism (EP=8) in the MoE layers, both riding the same eight physical chips. A config with that many moving parts has no shortage of plausible bottlenecks — sharding, routing, attention, the expert matmuls themselves. Anyone can name a suspect. The brief was just: profile it, and tell us where the step actually goes.

Our auto-research engine doesn't answer that kind of question by reasoning about the shapes on a whiteboard. It runs the thing, reads the trace, and only then says what's expensive — because the whiteboard answer and the silicon answer disagree more often than anyone likes to admit.

It profiled the config at the shape that actually ships — batch 512, matching the launch command's --max-num-seqs 512 — and read the category breakdown of a decode step straight off the trace:

CategoryShare of step time
Gather (MoE token routing/permute)48.5%
Collectives (AG + RS + AR + CP)~16%
Expert matmul (GMM)~5%

Gather was the single largest cost in the step — nearly ten times the actual expert matmul it feeds, and, once tallied against every other category in the trace, bigger than all of them. Nobody had to guess which part was expensive; the trace just said so.

02 — Chasing One Category to Source

Three Gathers, Two of Them Fake

Gather was now the confirmed bottleneck — the single largest category in the step, bigger than the expert matmul it feeds. That's a category, not an answer; the engine walked it back into the MoE dispatch code itself. Token routing on the expert-parallel path does three distinct gathers per layer, each with a different job and a different engine:

  • Gather 1 — token_indices[topk_argsort_indices] — main TPU core, XLA. Recovers, for each expert-sorted slot, which original token it came from.
  • Gather 2 — valid_rows_mask(...)[topk_argsort_revert_indices] — main TPU core, XLA. Un-sorts a validity mask back to token order.
  • Gather 3 — hidden_states_local[token_indices_sorted] — SparseCore, via a dedicated ragged_gather kernel. The actual token embeddings, reordered into expert-grouped rows for the matmul.

Broken down by cost, the category isn't three roughly-equal gathers. The 48.5% figure from section 01 came from one specific track — the main TPU core's XLA Ops timeline — and gather 3 runs somewhere else entirely: a dedicated Pallas kernel, sc_ragged_gather_v2, dispatched to the SparseCore. That's not a guess; it's checked directly, on the SparseCore's own per-subcore trace, the same way gathers 1 and 2 were checked on the main core's. (The per-gather numbers below are from a later, independent re-capture — same config, a fresh trace — which is why gather's share of the step reads 49.6% here instead of section 01's 48.5%: two separate profiling runs, not two different answers.)

GatherWhere it runsTrack measuredCost
Gather 1 — token_indicesMain TPU coreXLA Ops105.1 ms/step
Gather 2 — valid_rows_maskMain TPU coreXLA Ops19.9 ms/step
Gather 3 — hidden_states_localSparseCoresc_ragged_gather_v21.46 ms/step

Two different physical engines, two different timelines — gather 3's cost was never going to show up in the main core's 48.5% no matter how expensive it turned out to be. That's exactly why "it doesn't compete here" needed a real number instead of an assertion: checked directly, it's small — about 1.46 ms/step, consistent across the three SparseCore subcore lanes sampled (of 16 total), roughly 85× smaller than what gathers 1 and 2 cost together on the core that's actually the bottleneck. Gather 3 is real data movement — megabytes of hidden-state data, not an index trick — and it happens to also be cheap, on a different engine. Gather 1 is neither: expensive, on the main core, and — as it turns out — not moving real data at all. The difference only shows up if you read what it's gathering from, not just what it produces.

The array being gathered was never real data

token_indices is built fresh, immediately before the gather, as jnp.arange(num_tokens_local).repeat(topk) — [0,0,…,0, 1,1,…,1,…], each token index repeated topk times. No permutation, no mask, nothing applied to it before the gather runs. Which means, for every position i: 

token_indices[i] == i // topk

Gathering from an array that is itself a pure function of the index is identical to applying that function to the gather indices directly. So token_indices[topk_argsort_indices] — a real memory gather, with all the address-generation and scatter/gather-unit overhead that implies — is exactly equal to topk_argsort_indices // topk, a single integer division with no memory access pattern at all. 

# before — a gather dressed up as data movement
num_tokens_local = hidden_states_local.shape[0]
token_indices = jnp.arange(num_tokens_local, dtype=jnp.int32).repeat(topk)
token_indices_sorted = token_indices[topk_argsort_indices]

# after — the same result, no gather, no array to build
if envs.MOE_TOKEN_INDICES_USE_GATHER:      # A/B fallback, default off
    num_tokens_local = hidden_states_local.shape[0]
    token_indices = jnp.arange(num_tokens_local, dtype=jnp.int32).repeat(topk)
    token_indices_sorted = token_indices[topk_argsort_indices]
else:
    token_indices_sorted = topk_argsort_indices // topk

Before touching the kernel, the engine checked the identity the boring way — brute-force, across shapes, against NumPy — rather than trust its own algebra: 

for N, topk in [(37,2), (128,4), (5,1), (1000,8)]:
    token_indices = np.arange(N).repeat(topk)
    argsort_idx   = np.argsort(rng.integers(0, 16, size=N*topk), kind='stable')
    assert np.array_equal(token_indices[argsort_idx], argsort_idx // topk)
# identity verified across shapes

It also grepped the rest of the kernel for any other read of token_indices before deleting it — there wasn't one, so the array (and the now-unused row-count variable that fed it) came out entirely.

Gather 2 looked real. It wasn't, either.

The first pass over gather 2 called it settled: a boolean mask, genuinely indexed by a permutation, real data with no algebraic shortcut available. The engine started scoping a SparseCore kernel rewrite to move it off the main core, the same way gather 3 already runs there — reading through the target kernel's indirect-DMA pipeline, sizing up what extending it would take. That scoping is what forced a second, closer look at what valid_rows_mask actually computes: 

def valid_rows_mask(batch_size, group_sizes, group_start, group_end):
    group_sizes_sum = jnp.cumulative_sum(group_sizes, include_initial=True)
    token_start = group_sizes_sum[group_start]
    token_end = group_sizes_sum[group_end]
    index = jnp.arange(batch_size)
    return jnp.logical_and(token_start <= index, index < token_end)

Same shape of mistake as almost writing off gather 1: token_start and token_end are two scalars, computed once. Every entry of the mask is just is my row index inside this range — not a lookup into real per-row data. The exact same identity applies: 

# before
mask = valid_rows_mask(
    gmm1_res.shape[0], group_sizes, group_offset, group_offset + local_group_size,
)[topk_argsort_revert_indices].reshape(-1, topk, 1)

# after
token_start = group_sizes_sum[group_offset]
token_end = group_sizes_sum[group_offset + local_group_size]
mask = jnp.logical_and(
    token_start <= topk_argsort_revert_indices,
    topk_argsort_revert_indices < token_end,
).reshape(-1, topk, 1)

Verified the same way — 200 random trials, varying group counts, sizes, and shard spans, checked against the old gather byte-for-byte — before it touched the kernel.

The lesson wasn't in gather 1. It called gather 2 "real" on the first pass and moved on toward a kernel rewrite. The mistake wasn't in the code, it was stopping at the first plausible explanation instead of asking the same question — is this array actually data, or just a function of its own index? — of every gather in the function. The second time, it did.

Gather 3 got no such reprieve: it indexes the actual token embeddings — real, multi-kilobyte-per-row data with no algebraic shortcut available, which is exactly why it's the one already running on SparseCore. Two of three gathers turned out to be arithmetic wearing a memory operation's clothes; the third is the only one actually moving data.

03 — Shipping It, and Checking Its Own Homework

The Verification Loop Catches Itself

The fix landed behind MOE_TOKEN_INDICES_USE_GATHER — off by default, so the old gather path stays one environment variable away for a direct A/B rather than a leap of faith. Widened across seven and five steps captured on seven non-straggler chips, the result: gather down 87.6%, step latency down 19.8%.

Gather 2's turn

The gather-2 fix landed behind its own flag, MOE_VALID_ROWS_MASK_USE_GATHER — same pattern, off by default. First comparison:

Legacy gatherRange-checkΔ
Step latency452.4 ms/step391.9 ms/step−13.4%
Gather (routing)13.54 ms/step (10.5%)2.13 ms/step (1.4%)−84.3%

The gather-category collapse is exactly what deleting gather 2 predicts, and it's the direct, causal result of the change. The step-latency number came from an 8-step sample against a 3-step sample — small enough that a wider capture was queued before trusting it as a headline number.

That follow-up capture hit the same failure mode this post already caught once: at a longer, more decode-heavy output length, the profiler's JSON export capped at the same ~1,000,000-event ceiling that forced the earlier switch to the raw .xplane.pb — and this time the raw-trace fallback that saved that earlier case didn't get written at all, 0 bytes on both sides of the comparison. Rather than force a read on files that failed the exact way this post already learned to distrust, the engine reached for a strictly stronger source of truth instead of a bigger profiler capture: a real load test (next section). A second profiler attempt, back at the shorter output length that worked the first time, landed clean while that load test was running — six and seven full decode steps of real .xplane.pb data. "Three fixes" from here on, not two: alongside gathers 1 and 2, a smaller change also shipped to how per-expert token counts get computed (a sort-and-count instead of a one-hot matmul, worth roughly 1% on its own — a supporting fix, not a third act, so it isn't covered in depth here). All three on together against all three flipped back to legacy:

All legacyAll optimizedΔ
Step latency569.6 ms/step393.6 ms/step−30.9%
Gather (routing)126.1 ms/step (49.6%)2.3 ms/step (1.8%)−98.2%

That's all three fixes compounding, not just gather 2's share of it: the category that opened this post at roughly half a decode step (48.5% in the first pass, 49.6% in this wider re-capture) — bigger than the expert matmul it feeds — is now under 2%. What's left in "gather" is essentially gather 3 alone, the one gather that was always real.

Same three categories from section 01's opening table, same trace, all fixes on:

CategoryShare of step time
Gather (MoE token routing/permute)1.8%
Collectives (AG + RS + AR + CP)~38%
Expert matmul (GMM)~3%

Collectives look bigger now — not because they got more expensive (in absolute ms/step they're in the same ballpark as before, run-to-run noise aside), but because gather's collapse shrank the denominator. When the biggest thing in a step goes from 48.5% to 1.8%, everything else's share goes up mechanically, without a single line of that code changing. Gather stopped being the story; it's just not competing for attention anymore.

04 — Beyond the Profiler

512 Concurrent Requests, For Real

512 concurrent requests, 1024-token prompts, 1024-token generations, against a live vllm serve — the optimized defaults compared against the same legacy baseline used throughout this post. No profiler, no per-op accounting — just what a client waiting on tokens actually experiences.

MetricLegacy (all 3 flags)Optimized (default)Δ
Request throughput8.91 req/s9.57 req/s+7.4%
Output token throughput9,128.8 tok/s9,796.2 tok/s+7.3%
Mean TTFT6,251.8 ms4,423.3 ms−29.2%
P99 TTFT29,828.7 ms7,518.5 ms−74.8%
Mean TPOT44.82 ms41.89 ms−6.5%
P99 inter-token latency200.73 ms187.81 ms−6.4%

The number worth sitting with is P99 TTFT: 74.8% off the worst-case time to first token — more than ten times the throughput gain, on the same run. That's not a coincidence. TTFT is dominated by prefill, and prefill pushes the entire batch through the same gather-heavy MoE dispatch path a single decode step only samples a slice of. A 1024-token prefill runs proportionally more tokens through gathers 1 and 2 than any one decode step does, so arithmetic that used to be a memory gather compounds exactly where the tail latency lives — and where a real user waiting on a response feels it most.

The load test didn't find anything new — it confirmed what the op-level trace already predicted. Gathers 1 and 2 combined were the single largest cost in a decode step back in section 01, before any of this shipped, and prefill pushes more tokens through that same code path than decode does. The serving benchmark is the same finding, measured at the scale that actually reaches a request.

The meta-result matters more than the 87.6%, the 84% after it, or the 74.8% that confirmed both under load. Nothing in this post required a human to eyeball a flame graph. Profile at the shape that ships, walk one cost category back to the lines of source that produce it, prove an optimization algebraically before writing it, ship it behind a flag, re-run the comparison when a result doesn't add up — including the result that says "this one's fine, skip it" — and when the profiler itself fails, reach for a stronger source of truth instead of forcing a bad read. Point the loop at a serving command, and it comes back with the receipts, corrections included.
