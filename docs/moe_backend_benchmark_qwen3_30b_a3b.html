Background

fused_ep_moe (the dedicated fused MoE kernel, backend name FUSED_MOE) originally could not run at all under NEW_MODEL_DESIGN=1 DP-attention configurations like DP8_EP: its mesh validation required exactly one non-trivial axis, but DP8_EP's mesh has two — attn_dp (for cheap KV-cache sharding across this model's 4 KV heads) and model (the remaining tensor-parallel width). The kernel's RDMA device-id addressing was generalized to support a combined multi-axis expert-parallel group, unlocking FUSED_MOE under DP8_EP for the first time. A companion feature was then added — a per-num_tokens dynamic switch between the statically-selected GMM_EP backend and FUSED_MOE, gated by the MOE_FUSED_KERNEL_MAX_NUM_TOKENS env var — on the theory that FUSED_MOE might win at small (decode-like) token counts even if GMM_EP wins at large (prefill-like) ones.

Both changes were validated for correctness on real v6e-8 hardware against the kernel's reference implementation (including resolving a false-alarm investigation where near-tied top-8/top-9 routing decisions in naive random test data looked like a large discrepancy but were in fact two equally valid tie-breaks — not a bug). This page summarizes the separate, subsequent performance question: given both backends are correct, which one should actually be used, and at what num_tokens threshold, for this model on this hardware?

2. Kernel-level device-time sweeps

The end-to-end result only covers one operating point (concurrency 512). To find where, if anywhere, FUSED_MOE might win — and to pick a value for MOE_FUSED_KERNEL_MAX_NUM_TOKENS — a standalone microbenchmark (scripts/benchmarking/kernels/benchmark_moe_backend_sweep.py) sweeps num_tokens from 16 to 8,192 directly through moe_apply, at the model's exact production shape and mesh. Four legs are compared per point:

  • gmm_ep — the statically-selected production backend.
  • gmm_tp — the tensor-parallel GMM backend (different physical weight layout; shown for a full picture, not controlled by MOE_FUSED_KERNEL_MAX_NUM_TOKENS).
  • fused_moe (dynamic) — what the dynamic switch actually pays per call: weights are stored once as GMM_EP-formatted and relayouted to FUSED_MOE's format on every call, then run through fused_ep_moe.
  • fused_moe (native) — the kernel-only cost, with weights pre-converted once outside the timed call (as if the layer had statically selected FUSED_MOE at load time). Isolates the relayout's overhead from the kernel itself.

Timing is pure on-device execution time from an XLA profiler trace (summing device_duration_ps across a window of many back-to-back calls and dividing by the call count), not wall-clock — wall-clock timing was tried first and found to substantially overstate the fused_moe legs' cost due to Python dispatch/kernel-launch overhead (see Methodology notes).

Result

gmm_ep wins at every single num_tokens from 16 to 8,192, in both shardings — no crossover point exists anywhere in the tested range. fused_moe (native) gets closest at 1,024 tokens (0.83× production, 0.93× under attn_dp=8) but never exceeds 1.0×, and the gap widens again sharply past 1,024 tokens (down to ~0.35–0.39× at 8,192 — i.e. gmm_ep is ~2.8× faster at large scale). fused_moe (dynamic) is worse than native at every point because it additionally pays the weight-relayout cost on every call. gmm_tp ties gmm_ep only at the smallest token count (16) and loses elsewhere. The two shardings behave almost identically for gmm_ep/gmm_tp/dynamic; attn_dp=8 is a modest, consistent improvement specifically for fused_moe (native) at mid-to-large scale, but not enough to change the outcome.

Methodology notes

Wall-clock vs. device time

The sweep was first run with wall-clock timing (dispatch reps calls back-to-back, block once, divide elapsed time by reps). That measurement substantially overstated the fused_moe legs' true cost: at small scale, fused_moe (native) looked 2–2.6× slower than gmm_ep, when its real on-device cost is only 17–33% slower. The dynamic leg was affected even more, since its per-call weight relayout involves several separate eager ops, each carrying its own dispatch latency that wall-clock time counts but device time does not. Device time was obtained via jax.profiler.trace, summing every "XLA Modules" event's device_duration_ps across a trace window spanning exactly reps calls and dividing by reps — robust to a single logical call spanning more than one compiled module (true for the dynamic leg), unlike a naive per-call/per-module correspondence.

A resolved false alarm: near-tied routing

During correctness validation (not covered in the performance tables above), an early ad-hoc test showed a large (~30–45%) discrepancy between fused_ep_moe and the kernel's reference implementation at this model's shape. This was traced through several hypotheses (weight-conversion bug, process_moe_weights bug, wrong auto-tuned block sizes) and ultimately resolved as a test-methodology artifact: naive random gating scores over 128 experts with top_k=8 can leave the 8th/9th-ranked expert boundary nearly tied, and the reference implementation's external top_k and the kernel's internal top_k can resolve that tie differently for a handful of tokens — a large per-token difference that is not a bug. Using the same "force well-separated top-k" gating construction the kernel's own test suite uses resolved this cleanly (all checks passed within the suite's normal atol=rtol=0.05 tolerance). No correctness issue was found in the kernel, in process_moe_weights, or in the new dynamic-switch code.

Recommendation

Leave MOE_FUSED_KERNEL_MAX_NUM_TOKENS=0 (its default, disabled)

For Qwen3-30B-A3B on TPU v6e-8 under DP8_EP (either attn_dp=4/model=2 or attn_dp=8/model=1), gmm_ep should simply be the MoE backend, full stop. There is no num_tokens threshold at which switching to FUSED_MOE pays off — it loses at every scale tested, from a single small decode step (16 tokens) up through a large batch (8,192 tokens), whether or not the per-call weight-relayout cost is included.

This does not mean the DP8_EP mesh generalization or the dynamic-switch feature were wasted work: the kernel fix is a genuine, validated capability unlock (FUSED_MOE simply could not run under DP-attention before), and the dynamic-switch mechanism (MOE_FUSED_KERNEL_MAX_NUM_TOKENS) is available and correct for any future model/shape/sharding combination where the crossover this one lacks does exist — the sweep script exists precisely so that can be re-checked cheaply.
