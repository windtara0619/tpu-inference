tpu_inference · 10-commit SparseCore/MoE investigation · end-to-end verification

The Verified Delta

Ten commits added seven env-gated flags to tpu_inference's MoE/SparseCore dispatch path, each backed by its own profiling report. This is what happened when all seven were turned on together and served for real: a live vllm serve of Qwen3-30B-A3B on a real v6e-8, same commit, same benchmark, flags on vs. off — plus one flag that failed to compile on real hardware and had to be reverted before the number below was real.

01 · The ten commits

One thread, from a permutation fix to a verified number

26828ad5 through 3bb2a925 on main, chronological.

01

Permutation fix + MoE gather bottleneck 26828ad5, 03dc4cfc

A permutation bug fix in fused_moe_gmm.py, then MOE_GROUP_SIZES_USE_ONEHOT and MOE_VALID_ROWS_MASK_USE_GATHER: two legacy paths (one-hot group-size reduction, gather-based valid-rows mask) replaced by cheaper arithmetic that reuses the sort already needed for topk_argsort_indices.

02

ragged_gather_reduce report, then a revert c5e41a93, 5dc702f8

A dispatch-path report and 100 lines of new test coverage, then rolled back in the very next commit — a dead end walked back before it shipped. Only the report survived.

03

The SparseCore fixed-overhead finding 542b9f7b

RAGGED_GATHER_V2_DENSE_FALLBACK_MAX_OUT_SIZE: below 2,048 output rows, route to a plain dense TensorCore gather instead of SparseCore — found by benchmarking the kernel directly against its own dense fallback across every shape seen in real MoE traffic.

04

Anatomy, efficiency: the planning pair a97b545f, 5b7395a5

Two reports (Two Steps, Four Costs, Full Occupancy, Empty Decode) mapping the encode/decode step anatomy and SparseCore idle time — the groundwork that pointed at the inner-pipeline restart cost investigated next.

05

The stall reproduction and the subchunk cap 00169be2

A 475-line test reproduces the SparseCore stall directly from a captured trace, calibrated to two decimal places against real production traffic, and debunks a previously reported 64%-stall figure (closest real number: 26.4%). Adds RAGGED_GATHER_V2_MAX_NUM_ROW_SUBCHUNKS: default 4 (unchanged), 8 trades a ~1.7× regression on small windows for 11–13% on windows ≥2,048 rows.

06

Extending the fix, and updating experiments ba40e1bf, 3bb2a925

The subchunk cap and a new interleaved row-partition-assignment mode (RAGGED_GATHER_REDUCE_V2_INTERLEAVE_ROW_PARTITIONS) extended to ragged_gather_reduce_v2, plus a combine-stats logging flag. All new defaults preserve current behavior — every one of these seven flags is opt-in until this report.

Reading the p99 TTFT move

The largest single move — 70% off p99 time-to-first-token — lines up with what docs/report_inner_pipeline_stall.html predicted for RAGGED_GATHER_REDUCE_V2_INTERLEAVE_ROW_PARTITIONS: contiguous row-partitions correlate with token/batch position, so a shard can land almost entirely outside its local-expert range on an unlucky prefill batch, stalling that request's first token behind a near-empty SparseCore call. Interleaving breaks that correlation.

04 · What tripped on the way

Two failed boots before the first clean run

Neither is a flag bug — both are gaps in the reproduction, worth recording so the next person skips them.

Missing NEW_MODEL_DESIGN=1

config gap 
pydantic_core._pydantic_core.ValidationError: 1 validation error for VllmConfig
  Value error, Must run Attention DP with NEW_MODEL_DESIGN enabled. Please set NEW_MODEL_DESIGN=True

dp_attention requires NEW_MODEL_DESIGN=1 unconditionally — not specific to the 397B model this repo's reference server.sh was written for. Both boots failed in under a minute; no TPU time or download wasted.

--random-range-ratio is inverted from intuition

benchmark-client gap 
ValueError: --random-input-len is too small: with tokenizer special tokens 0 and
input range ratio 1.0, the minimum possible total input tokens is 0.

In vllm bench serve's random dataset, range_ratio is the amount of variance around the mean length, not a fixed-length toggle — 1.0 is maximum variance (degenerates to zero-length prompts at the low end) and 0.0 is fixed-length. Fixed at 0.0 for a clean 1,024-in/1,024-out comparison.

05 · The new finding

cap=8 on the reduce kernel doesn't compile

Not documented anywhere in the 10 commits — this run is the first time it was tried on real hardware.

RAGGED_GATHER_REDUCE_V2_MAX_NUM_ROW_SUBCHUNKS=8

compile failure on real hardware 
jax.errors.JaxRuntimeError: INTERNAL: Failed to run MLO pass
pipeline.sc_ragged_gather_reduce_v2.195:147:1: error: 'memref.alloca' op
E3000: CompileTimeSparseCoreAllocationFailure: current allocation offset
upper bound (28 words) exceeds the legitimate user allocatable offset
upper bound (27 words) in memory space sflag_tile when allocating 2 words

ba40e1bf extended the subchunk-cap knob from ragged_gather_v2 to ragged_gather_reduce_v2, but the cap=8 sweep in 00169be2 was only ever run against the plain gather kernel — the commit message for the extension says as much: “has never had this be configurable before”. The reduce kernel carries additional per-subchunk scalar-flag state that the gather kernel doesn't, and at cap=8 that state overflows SparseCore's sflag_tile allocation by 2 words at compile time on this v6e-8. The improved run above keeps this one flag at its default (4) and gets the rest of the win from the other six flags.

Follow-up

Worth a fix or a doc update on ba40e1bf: either cap the effective value for the reduce kernel below 8, or note in envs.py that values above 4 are unvalidated for ragged_gather_reduce_v2 and may not compile depending on TPU generation and shape.
